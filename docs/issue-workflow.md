# Issue駆動開発プロセス

このドキュメントは、要望・要件をGitHub Issueとして起票してから、開発計画・実装・レビューを経てPRをマージするまでの
定型手順をまとめたものである。Claude Code向けの自動トリガーとしては`.claude/skills/issue-workflow/SKILL.md`
が本ドキュメントの要約版として存在し、「Issueにまとめて」「Issueを元にPRを作って」等の依頼で自動的に
この手順に従う。

## 1. 目的・適用範囲

- 変更の規模とリスクに応じて、**標準経路**（2節以降の全工程）と**軽量経路**（1.1節）を使い分ける。
  どちらの経路でも、CIの必須チェックと`docs/process/dod.md`（完了の定義）は同じように適用する
- 目的は、要望の言語化と実装のトレーサビリティ確保（「なぜこの変更をしたか」「どう作ると決めたか」が
  IssueとPRに残る）
- `docs/implementation-plan.md`はプロジェクト初期（Phase 0〜8）の全体計画であり、Issueごとの開発計画ではない。
  Issueごとの開発計画は、4節以降のとおり**下書き（draft）PRの本文**に書く

### 1.1 経路の選択（標準経路／軽量経路）

PoCの目的は早く学ぶことであり（`docs/process/poc-definition.md`）、小さな変更にまで全工程を踏むと試して学ぶ速度が落ちる。
一方で、AIのレビュー工程を増やしても人の判断が入る点は増えない。そこで、**次の条件をすべて満たす変更は軽量経路**で進める。
1つでも外れる、または判断に迷う場合は標準経路にする。

| 条件 | 確かめ方 |
|---|---|
| 差分が300行未満（テストを含む、`package-lock.json`などの生成物を除く） | `git diff --stat main...HEAD` |
| `src/domain/`の業務ロジック（テスト以外）を変更しない | 差分のファイル一覧 |
| 依存関係（`package.json`）・CI（`.github/workflows/`）・`.claude/`配下のエージェント／フック設定を変更しない | 差分のファイル一覧 |
| 外部入力の扱い（JSON・CSVの入出力、`scenarioIO.ts`・`masterIO.ts`・`csvExport.ts`など）を変更しない | 差分のファイル一覧 |
| `docs/v5-spec.md`の解釈・`docs/design.md`のEXT-xxの追加や変更を伴わない | 開発計画の時点で判断 |

軽量経路の例：文書の修正、テストの追加（期待値は仕様から作る）、画面の文言・余白・色トークンの調整、既存のふるまいを
変えない小さなリファクタリング。

| 工程 | 標準経路 | 軽量経路 |
|---|---|---|
| Issue（3節） | 起票する（仕様レビュー・承認ゲートあり） | 起票しなくてよい。PR本文の冒頭に目的を1〜2行で書く（ユーザーが依頼した変更であることが分かるようにする） |
| 開発計画（5節） | 下書きPRの本文に書く | PR本文に変更点と確認方法を短く書く |
| 計画レビュー（6節） | 3観点で行う | 行わない |
| 実装レビュー（8節） | 変更範囲に応じて`logic-reviewer`・`ux-reviewer`・`/security-review` | UI変更があれば`ux-reviewer`のみ。それ以外は省略 |
| PRレビュー（10節） | `/code-review`＋5観点の確認＋人の確認 | `/code-review`＋人の確認（`docs/process/dod.md` D7） |
| CI・DoD・`CHANGELOG.md`への追記 | 必須 | 必須（変わらない） |

- PR本文の冒頭に、どちらの経路で進めたかを書く（`経路：軽量`／`経路：標準`）
- 作業の途中で条件を外れたら（差分が膨らんだ、ドメインロジックに触れる必要が出た等）、その時点で標準経路に切り替え、
  残りの工程（計画レビュー以降）を行う
- 差分が500行を超える見込みの変更は、標準経路でも開発計画の段階で分割を検討する（レビューで見落としが増えるため）

## 2. 全体の流れ（標準経路）

| # | 工程 | 成果物・記録先 | 担当 |
|---|---|---|---|
| 1 | Issue下書き（3節） | チャット上の下書き | Claude |
| 2 | 仕様レビューと反映（3節） | 改善済みの下書き | `issue-spec-reviewer` |
| 3 | 承認ゲート → Issue起票（3節） | GitHub Issue | ユーザーが承認 |
| 4 | ブランチ作成（4節） | `issue-<番号>-<短い説明>` | Claude |
| 5 | 開発計画 → 下書きPR作成（5節） | 下書きPRの本文「開発計画」 | Claude |
| 6 | 計画レビューと反映（6節） | PR本文「計画レビュー結果」 | `logic-reviewer`・`ux-reviewer`・`security-reviewer` |
| 7 | 実装・テスト（7節） | コミット、PR本文のタスクのチェック | Claude |
| 8 | 実装レビュー（8節） | 修正コミット、`docs/security/reports/` | `logic-reviewer`・`ux-reviewer`・`/security-review` |
| 9 | 実装結果の記録 → Ready for review（9節） | PR本文「実装結果」「受け入れ条件の充足」、CI | Claude |
| 10 | PRレビュー（10節） | PRのレビューコメント | Claude（`/code-review`）とユーザーの両方 |
| 11 | マージ・マージ後の対応（11節） | Issueの自動クローズ（`CHANGELOG.md`への追記はマージ前に済ませる） | ユーザーがマージ |

## 3. Issue作成（下書き・仕様レビュー・承認ゲート）

### 3.1 下書き

- `.github/ISSUE_TEMPLATE/feature_request.md`（汎用1種類）の構成で下書きを作る。この時点ではまだ起票しない
- 受け入れ条件は「`npm test`等で検証可能な粒度」で書く。曖昧な希望ではなく、完了状態が判定できる形にする
- 関連する`docs/v5-spec.md`・`docs/design.md`の節がある場合は「参考資料」欄に明記し、
  仕様上の根拠をたどれるようにする

### 3.2 仕様レビュー

- Issue下書きを`issue-spec-reviewer`サブエージェント（`.claude/agents/issue-spec-reviewer.md`）に渡し、
  自動でレビューさせる
- 確認観点は5つ：①要件が達成する目的・効果の明確さ、②曖昧さの解消・実現可能なレベルへの分解、
  ③`CLAUDE.md`・`docs/design.md`が定める開発方針との整合性、④実装の費用対効果（定性判定：軽／中／重）、
  ⑤`.github/ISSUE_TEMPLATE/feature_request.md`の必須項目の充足
- エージェントは指摘サマリと**改善済みの下書き本文**を返す（レビュー結果の反映はこの時点で済んでいる）。
  開発方針と矛盾する要求など、レビューだけでは解決できない論点は下書きの末尾に「レビュー時の確認事項」として
  残し、ユーザーの判断を仰ぐ

### 3.3 承認ゲート

- 仕様レビュー後の**Issue本文の下書き**をチャット上に提示し、実際にGitHub Issueとして
  起票する前にユーザーの承認を待つ
- 承認前に4節以降（ブランチ作成・開発計画・実装・PR作成）へ進めない。修正依頼があれば下書きに反映し、
  再度提示する（軽微な修正であれば3.2の仕様レビューをやり直さなくてよい）
- 承認が得られたら、その内容でIssueを起票する

## 4. ブランチ作成

- Issue番号を含むブランチ名にする（例：`issue-<番号>-<短い説明>`）
- Claude Code on the webから起票する場合はセッションが払い出すブランチ名（`claude/...`等）をそのまま使う

## 5. 開発計画（下書きPR）

- Issueの要件・受け入れ条件と既存コードを読んで開発計画を立て、それを本文に書いた**下書き（draft）PR**を作る。
  PR本文は`.github/PULL_REQUEST_TEMPLATE.md`を使い、先頭の`Closes #<Issue番号>`と「開発計画」節を埋める
  （「実装結果」以降は9節で埋める）
- 開発計画に書く内容：
  - **方針**：どう実現するか。既存の設計判断（`CLAUDE.md`「実装時に確認すべき設計判断」、`docs/design.md`の
    EXT-xx）との関係、別案を採らなかった理由
  - **変更予定ファイル**：追加・変更するファイルと変更の要点
  - **タスク**：実装・テスト・ドキュメント更新を、1つずつ完了を判定できる粒度のチェックリストにする
  - **受け入れ条件の検証方法**：Issueの受け入れ条件1件ごとに、どのテスト・どの操作で確かめるか
  - **リスク・未決事項**：`docs/design.md` §3への追記が必要になりそうな解釈、影響範囲の大きい変更など
- ブランチにまだコミットが無いとPRを作れないため、`git commit --allow-empty -m "Issue #<番号> 着手（開発計画）"`
  で着手コミットを1つ作ってpushしてから、下書きPRとして作成する
- 下書きPRのうちはCIやPRプレビューが動いても構わない（レビュー依頼ではない）

## 6. 計画レビュー

- 下書きPRの本文（開発計画）とIssue本文を、以下の3つのサブエージェントに「計画レビュー」として渡す。
  コードはまだ無いので、各エージェントは計画の記述と既存コード・ドキュメントを突き合わせてレビューする

  | 観点 | レビュアー | 見ること |
  |---|---|---|
  | 要件と実装方針の整合性・合理性 | `logic-reviewer` | Issueの要件・受け入れ条件を計画が漏れなく満たすか、`v5-spec.md`・`design.md`・`CLAUDE.md`の方針と矛盾しないか、より単純な方法が無いか、検証方法で受け入れ条件を判定できるか |
  | UI/UXの妥当性・利便性・操作性 | `ux-reviewer` | 画面・導線・メッセージ・アクセシビリティの計画が、既存画面と一貫し教材として分かりやすいか |
  | セキュリティの安全性・堅牢性 | `security-reviewer` | `docs/security/checklist.md`のうち計画に関係する観点（外部入力の検証、ファイル入出力、依存追加、CI権限など） |

- 3観点とも実施を原則とする。明らかに該当しない観点（例：UI変更が無い場合のUI/UX）は省略してよいが、
  省略した旨と理由を記録する
- 指摘を計画に反映してPR本文を更新し、「計画レビュー結果」欄に観点ごとの主な指摘と対応（反映した／反映しない理由）
  を記録する
- レビューだけでは決められない論点（Issueのスコープ変更、設計方針の転換など）は、実装に入る前にユーザーに確認する

## 7. 実装・テスト

- 計画のタスクに沿って実装し、終わったタスクはPR本文のチェックリストにチェックを付ける
- `CLAUDE.md`の既存ルール（ドメインロジックの分離、BOM再帰探索の訪問済み集合、マスタ編集ガードの集約先など）
  を踏襲する
- 仕様の解釈・追加決定が必要になった場合は、`docs/v5-spec.md`本体は直接編集せず`docs/design.md` §3に追記する
- 実装中に計画を変える必要が出たら、PR本文の計画を更新し、「計画からの変更点」に理由を書く
- コミット前にローカルで`npm run lint`・`npm run build`（型チェックを含む）・`npm test`を通す

## 8. 実装レビュー

計画レビューと同じ3観点で、今度は実装したコードを対象にレビューする。

- `src/domain/`配下を変更した場合は`logic-reviewer`でv5-spec.md・design.mdとの整合性を確認する
- `src/components/`配下を変更した場合は`ux-reviewer`で操作性・アクセシビリティを確認する
- `/security-review`（`.claude/commands/security-review.md`）を実行し、差分を`security-reviewer`に検査させる。
  手順の詳細と、指摘があった場合の扱い（テスト追加→失敗したら修正案を提示し承認を得てから修正）は
  `CLAUDE.md`「セキュリティレビュー」節に従う。レポートは`docs/security/reports/`に出力される

## 9. 実装結果の記録とReady for review

- PR本文の「実装結果」（概要・変更理由・実装内容・計画からの変更点）、「受け入れ条件の充足」、「テスト」、
  「確認事項」を埋める（各チェック項目は完了の定義`docs/process/dod.md`のD1〜D8に対応する）。「人の確認」欄はマージする人が
  記入するため、Claudeは埋めない。実装結果はPRのコメントではなく本文に書く（本文が常に最新の状態を表すようにするため）
- 「受け入れ条件の充足」には、Issueの受け入れ条件1件ごとに、対応する実装・テスト（ファイル名・テスト名）と結果を書く
- CI（`.github/workflows/test.yml`）がgreenであることを確認する。CIのジョブは次の3つ：
  - `test`：lint（`npm run lint`）・型チェックとビルド（`npm run build`）・vitest（`npm run test:coverage`）
  - `a11y`：Playwright＋axe-coreによるアクセシビリティ検査（`npm run test:a11y`）
  - `e2e-scenario`：業務シナリオのE2Eテスト（`npm run test:e2e:scenario`）
- UI変更がある場合は、PRに自動でコメントされるPRプレビューURL（`pr-preview.yml`）で動作を確認できる
- `main`はRulesetで`test`・`a11y`・`e2e-scenario`の成功を必須にしているため、CIが完了・成功するまでマージできない
- 上記がそろったら下書きを解除し、Ready for reviewにする

## 10. PRレビュー

Claude（`/code-review`）とユーザーの**両方**がレビューする。

### 10.1 確認観点（両者共通）

1. **PRと実装の整合性**：PR本文の「実装内容」「変更予定ファイル」と実際の差分が一致しているか。計画に無い変更が
   含まれていないか（含まれる場合は「計画からの変更点」に理由があるか）
2. **想定タスクの実施**：開発計画のタスクがすべてチェック済みか。未実施のものに理由が書かれているか
3. **受け入れ条件の充足**：Issueの受け入れ条件1件ごとに、対応する実装・テストと結果が示されているか
4. **品質ゲート**：CIがgreenか。計画レビュー・実装レビュー（`/security-review`を含む）の指摘が対応済みか
5. **確認事項**：`docs/design.md`・`CLAUDE.md`の更新要否が判断されているか

### 10.2 Claudeのレビュー

- `/code-review --comment`で差分の不具合を検査し、指摘をPRにインラインコメントとして投稿する
- あわせて10.1の観点1〜5の確認結果を、PRのコメントに1件の表としてまとめて投稿する
- 指摘があれば修正してpushし、該当スレッドに対応内容を返信してから、再度10.1を確認する

### 10.3 ユーザーのレビュー

- Claudeのレビュー結果を参考に、10.1の観点で確認する。必要に応じてPRプレビューで実際の画面を操作する
- あわせて`docs/process/dod.md`の「人が確認する範囲」（D7）を確認し、PR本文の「人の確認」欄にチェックを付ける。
  AIが書いたコード・テストを含め、成果物の責任はマージする人が持つ
- 問題が無ければマージし（11節）、修正が必要ならPRにコメントする（Claudeが対応してpushする）。
  開発者が1名のため、GitHub上のApprove（自分のPRは承認できない）は求めない

## 11. マージ・マージ後

- マージはユーザーが行う（Claudeはマージしない）
- Issueが自動クローズされたことを確認する
- 実装の記録はマージ前にそのPRの中で`CHANGELOG.md`へ追記しておく（9節・`docs/process/dod.md` D8）。マージ後に
  記録だけの別PRは作らない。`CLAUDE.md`「現在の実装状況」「次にやるべきこと」は、要約が変わる場合だけ同じPRで更新する

## 12. 複数Issueの並行実装

複数のIssueを指定して同時並行で実装するよう依頼された場合は、4節（ブランチ作成）に入る前に以下の手順で
衝突を回避する。3節〜11節の手順自体はIssueごとに変わらず、そのまま並行して適用する。

- **①footprintチェック**：対象Issueそれぞれの本文（要件・受け入れ条件）を読み、影響しそうな
  `src/domain/*.ts`・`src/components/*.tsx`等のファイルを`Grep`/`Glob`で洗い出す。当てずっぽうで
  判断しないこと
- **②グルーピング**：影響ファイルの見込みが重ならないIssue同士だけを同時並行の対象にする。重なりが
  見込まれるIssueは同時に走らせず、順番に処理する（先に着手した方をマージしてから後続に着手する）
- **③実行の分離**：並行実行するIssueは、Issueごとに別ブランチ・別の作業領域で進める。同一の作業
  ディレクトリで複数のIssueを同時に編集しないこと（同じファイルを同時に上書きする事故につながる）。
  具体的には次のいずれかを使う：
  - Claude Code Remoteの`create_session`で1 Issue = 1セッション（別コンテナ・別ブランチ）に払い出す
  - Agentツールを`isolation: "worktree"`で使い、サブエージェントごとに独立したgit worktreeを与える
- **④ブランチ名**：各Issueは4節の`issue-<番号>-<短い説明>`（またはセッションが払い出すブランチ名）を
  そのまま使い、並行していてもどのブランチがどのIssueに対応するか追跡できるようにする
- **⑤想定外の重なりへの対処**：①のfootprintチェックは見積もりであり完全な保証ではない。実装中に
  想定外に同じファイルへ触れた、あるいは後発のPRがマージ時にコンフリクトした場合は、通常のgit conflict
  解消（後発ブランチへ先行マージ済みのベースブランチを取り込んで解消する）で対応する。無理に同時マージ
  しようとしない
