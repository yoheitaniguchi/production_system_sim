# Issue駆動開発プロセス

このドキュメントは、要望・要件をGitHub Issueとして起票してから、実装・レビューを経てPRをマージするまでの
定型手順をまとめたものである。Claude Code向けの自動トリガーとしては`.claude/skills/issue-workflow/SKILL.md`
が本ドキュメントの要約版として存在し、「Issueにまとめて」「Issueを元にPRを作って」等の依頼で自動的に
この手順に従う。

## 1. 目的・適用範囲

- typo修正など軽微な変更を除き、機能追加・改善は必ずIssue化してから着手する
- 目的は、要望の言語化と実装のトレーサビリティ確保（「なぜこの変更をしたか」がPRだけでなくIssueにも残る）

## 2. Issue作成

- `.github/ISSUE_TEMPLATE/feature_request.md`（汎用1種類）を使う
- 受け入れ条件は「`npm test`等で検証可能な粒度」で書く。曖昧な希望ではなく、完了状態が判定できる形にする
- 関連する`docs/v5-spec.md`・`docs/design.md`の節がある場合は「参考資料」欄に明記し、
  仕様上の根拠をたどれるようにする

## 3. 仕様レビュー

- Issue下書きを`issue-spec-reviewer`サブエージェント（`.claude/agents/issue-spec-reviewer.md`）に渡し、
  自動でレビューさせる
- 確認観点は5つ：①要件が達成する目的・効果の明確さ、②曖昧さの解消・実現可能なレベルへの分解、
  ③`CLAUDE.md`・`docs/design.md`が定める開発方針との整合性、④実装の費用対効果（定性判定：軽／中／重）、
  ⑤`.github/ISSUE_TEMPLATE/feature_request.md`の必須項目の充足
- エージェントは指摘サマリと改善済みの下書き本文を返す。開発方針と矛盾する要求など、レビューだけでは
  解決できない論点は下書きの末尾に「レビュー時の確認事項」として残し、ユーザーの判断を仰ぐ
- レビュー後の下書きを次節（承認ゲート）でユーザーに提示する

## 4. 承認ゲート

- 仕様レビュー後の**Issue本文の下書き**をチャット上に提示し、実際にGitHub Issueとして
  起票する前にユーザーの承認を待つ
- 承認前に5節以降（ブランチ作成・実装・PR作成）へ進めない。修正依頼があれば下書きに反映し、
  再度提示する（軽微な修正であれば3節の仕様レビューをやり直さなくてよい）
- 承認が得られたら、その内容でIssueを起票する

## 5. ブランチ作成

- Issue番号を含むブランチ名にする（例：`issue-<番号>-<短い説明>`）
- Claude Code on the webから起票する場合はセッションが払い出すブランチ名（`claude/...`）をそのまま使う

## 6. 実装

- `CLAUDE.md`の既存ルール（ドメインロジックの分離、BOM再帰探索の訪問済み集合、マスタ編集ガードの集約先など）
  を踏襲する
- 仕様の解釈・追加決定が必要になった場合は、`docs/v5-spec.md`本体は直接編集せず`docs/design.md` §3に追記する

## 7. 実装レビュー

- `src/domain/`配下を変更した場合は`logic-reviewer`サブエージェントでv5-spec.md・design.mdとの整合性を確認する
- `src/components/`配下を変更した場合は`ux-reviewer`サブエージェントで操作性・アクセシビリティを確認する

## 8. PR作成

- `.github/PULL_REQUEST_TEMPLATE.md`を使う
- 先頭の`Closes #<Issue番号>`でIssueと自動リンクし、マージ時にIssueが自動クローズされるようにする
- CI（`.github/workflows/test.yml`：型チェック・ビルド・`npm test`）がgreenであることを確認してからレビューを依頼する

## 9. マージ後

- Issueが自動クローズされたことを確認する
- 実装状況の変化を`CLAUDE.md`「現在の実装状況」「次にやるべきこと」に反映する（対応不要ならその判断も
  PRの「確認事項」チェックリストで明示しておく）
