# セキュリティレビュー チェックリスト

`security-reviewer`エージェント・`/security-review`スラッシュコマンドが参照する正本。観点は
「§6.1 コードレベル」「§6.2 E2Eレベル」「§6.3 非機能面」の3部構成とし、各項目は本リポジトリの
実態（後述「前提」）に合わせて調整してある。

`security-reviewer`は各項目について、該当箇所がある場合は「ファイル:行」「根拠」「重大度
（Critical/High/Medium/Low/Info）」を、該当なしの場合は「該当なし＋理由」を記録すること。
重大度は「実際に悪用可能で影響が大きい＝High以上、到達不能・理論上のみ＝Low」を基準とし、
断定できない場合は根拠と不確実性を併記して**推測で重大度を上げない**こと。

## 前提（本リポジトリの実態）

- **バックエンドを持たないクライアントのみのSPA**（React + TypeScript + Vite）。認証・セッション・
  DBは無く、状態はブラウザのメモリ内のみ（`useReducer`）。永続化するのは`theme.ts`のテーマ選択の
  1件のみ（localStorage、機密性なし）
- データは教材用の架空データ（木製イス／自転車プリセット）。実在の個人情報・取引先情報は扱わない前提
- 既存の検証はexternalライブラリ（zod等）を使わず、`masterIO.ts`・`scenarioIO.ts`が宣言的な
  自前スキーマ検証を実装している。フィールドを個別に取り出して新規オブジェクトを組み立てる方式で、
  `JSON.parse`結果を直接spread/Object.assignしていない
- E2Eツールは導入済み（Playwright、`e2e/`配下）。CIは`.github/workflows/test.yml`
  （test/a11y/e2e-scenarioの3ジョブ）・`deploy.yml`・`pr-preview.yml`・`flaky-check.yml`
- 依存関係は`package-lock.json`をコミット済み、`npm ci`で再現可能

## §6.1 コードレベル

### インジェクション・XSS
- `dangerouslySetInnerHTML`、`innerHTML`、`outerHTML`、`insertAdjacentHTML`、`document.write`の使用
- `eval`、`new Function`、文字列引数の`setTimeout`/`setInterval`
- ユーザー入力・URLパラメータ・インポートデータ（マスタJSON・シナリオJSON）を未検証でDOM・属性・
  `href`/`src`（`javascript:`スキーム）に渡していないか
- 動的な`<a target="_blank">`に`rel="noopener noreferrer"`が付いているか（`BurgerMenu.tsx`等の
  外部リンク導線を含む）
- 正規表現のReDoS（入れ子の量指定子、ユーザー入力から動的生成するRegExp）

### 入力検証・データ取り込み
- `masterIO.ts`・`scenarioIO.ts`のJSONインポートでの型・スキーマ検証の有無（zod等は未導入。
  自前検証の抜け穴が無いか）
- `Object.assign`、スプレッド、再帰マージ、`JSON.parse`結果のマージによるプロトタイプ汚染
  （`__proto__`, `constructor`, `prototype`）
- ファイルサイズ・行数・ネスト深度の上限（マスタ・シナリオJSONインポート）
- 数値入力の範囲・NaN・Infinity・負数・巨大値の扱い（`mrp.ts`の所要量計算・`masterData.ts`の
  数量入力等が無限ループ・スタックオーバーフローを誘発しないか）
- BOM等の再帰構造での循環参照検出（CLAUDE.md記載の方針どおり訪問済み集合・深さ上限があるか。
  `masterIntegrity.ts`の`findBomCycles`等）
- **CSVエクスポート（`csvExport.ts`のescapeCsvField）がセル先頭の`=`/`+`/`-`/`@`によるCSV数式
  インジェクションに対応していない**（マスタ編集可能な品目名・作業区コード等がCSVに載る画面がある）

### ブラウザストレージ・状態管理
- localStorage（`theme.ts`が唯一の永続化）に機密情報・個人情報を保存していないか
- 保存データ（テーマID）読込時の検証（`isThemeId`によるホワイトリスト検証）が改ざん耐性を持つか
- URL・履歴・クエリパラメータからの状態復元機構の有無（現状は無い想定。あれば検証）

### シークレット・情報漏洩
- ソース・設定・テストデータ・コミット履歴へのAPIキー・トークン・パスワード・秘密鍵のハードコード
- `VITE_`プレフィックス環境変数の使用有無・機密値の混入（クライアントバンドルに露出する）
- `console.log`/エラー表示への機密・個人情報の出力
- ソースマップの本番公開設定（`vite.config.ts`のbuild設定）
- `.env*`が`.gitignore`に含まれているか

### 暗号・乱数
- セキュリティ用途（ID・トークン）での`Math.random`使用（`crypto.getRandomValues`を使うこと）。
  現状ID採番は`domain/*.ts`内の連番方式で外部から推測されても実害が無い教材データである点も踏まえて評価
- 独自暗号実装、弱いハッシュ（MD5、SHA1）の使用

### 依存・サプライチェーン（コード側）
- `postinstall`等のスクリプトを持つ不審な依存、未使用・放棄された依存
- CDNからの外部スクリプト/スタイル読込（SRI `integrity`未指定）。本リポジトリはCDN読込を
  使っていない想定（確認すること）
- `package-lock.json`がコミットされているか（コミット済み）、バージョン固定の方針

### TypeScript / React固有
- `any`や`as`型アサーションによる検証すり抜け（外部入力＝JSONインポート・ユーザー入力に対して）
- `useEffect`内の外部入力を使った動的`import()`/`fetch`のURL組み立て（バックエンド無しのため
  fetch自体がほぼ無い想定。あれば重点確認）
- iframe、`postMessage`のorigin未検証

## §6.2 E2Eレベル

E2Eツール（Playwright、既存の`e2e/`配下の流儀に合わせる）で、実ブラウザ上の挙動として検証する。

- **XSS実挙動**：全入力フォーム（受注・マスタCRUD等）・JSONインポート機能に、`<script>`、
  `<img onerror>`、`"><svg onload>`、`javascript:` URL等のペイロードを与え、スクリプトが実行
  されない（ダイアログ・グローバル変数の副作用が発生しない）こと、表示がエスケープされること
- **不正データインポート**：壊れたJSON、型不一致、巨大ファイル、深いネスト、`__proto__`を含む
  データ（マスタJSON・シナリオJSON）を取り込んでも、アプリがクラッシュせず、エラー表示で安全に
  拒否し、`Object.prototype`が汚染されないこと
- **境界値・異常入力**：受注数量・納期等の入力欄に、空、極端に長い文字列、負数、0、巨大数、NaN、
  絵文字・制御文字・RTL文字を入力しても、画面フリーズや無限ループが発生しないこと（タイムアウトを
  設定して検証）
- **ストレージ改ざん耐性**：localStorage（テーマキー）の保存値を不正な内容に書き換えてリロード
  しても、アプリが起動し、安全な初期状態（既定テーマ）に復帰すること
- **URLパラメータ改ざん**：状態復元の仕組みは現状無い想定（無いことを確認するか、あれば検証）
- **セキュリティヘッダー/CSP**：`vite preview`（本番相当ビルド配信）のレスポンスヘッダーに、CSP、
  `X-Content-Type-Options`、`Referrer-Policy`、`X-Frame-Options`（または`frame-ancestors`）が
  設定されていること。GitHub Pages配信はレスポンスヘッダーをカスタマイズできないため、
  `<meta>`タグでの代替可否も整理する
- **外部通信**：想定外の外部ドメインへのリクエストが発生しないこと（ネットワークリクエストを監視し、
  許可リスト外を検出）。バックエンド無しのため通常は0件のはず
- **コンソール漏洩**：通常操作・異常操作で、機密・個人情報がコンソールやエラー画面に出ないこと
- **クリックジャッキング**：別オリジンのiframeに埋め込めないこと（ヘッダー設定との整合）
- **アクセシビリティ経由の誘導（任意）**：外部リンクの遷移先表示、警告表示の有無

制約：E2Eの攻撃的入力は**ローカルで起動したアプリに対してのみ**行う。外部サービスへは実行しない。

## §6.3 非機能面

### 依存パッケージの脆弱性・ライセンス
- `npm audit --omit=dev`の結果でhigh/critical が0件であること（dev依存は別枠で報告）
- 脆弱性が無修正の場合、影響範囲（実際に到達可能か）と暫定対策を記載
- ライセンス一覧を出力し、GPL/AGPL等の強いコピーレフト、ライセンス不明のものを指摘（教材リポジトリ・
  GitHub Pages公開という前提を明記）
- 更新が長期間停止した依存、メジャーバージョン遅れの一覧
- ロックファイルの整合性、`npm ci`で再現可能であること
- Dependabot等の自動更新設定の有無（現状未設定）

### シークレット・設定不備
- コミット履歴を含むシークレットスキャン（gitleaks等、未導入。導入案は提示するが導入は承認後）
- GitHub Actions：ワークフロー（`test.yml`・`deploy.yml`・`pr-preview.yml`・`flaky-check.yml`）の
  `permissions`が最小権限か、サードパーティAction（`peaceiris/actions-gh-pages`・
  `rossjrw/pr-preview-action`等）がSHA固定か、`pull_request_target`の危険な使用、シークレットの
  ログ出力、`GITHUB_TOKEN`の権限
- Vite/ビルド設定：本番ビルドでのソースマップ、`define`で埋め込まれる環境変数、開発サーバーの
  `host`公開設定（`0.0.0.0`）、CORS設定
- ホスティング設定（GitHub Pages）でヘッダーを設定できるか。できない場合は`<meta>`での代替可否を整理
- ブランチ保護、必須レビュー、CODEOWNERSの有無（現状CODEOWNERS未設定。リポジトリ設定は確認のみ・
  変更は提案）

### ログ・個人情報・可用性
- ログ・分析・エラー送信に個人情報や機密情報が含まれないこと（現在のデータは架空の教材データである
  ことを確認して明記）
- 個人情報を扱う入力欄があるか（得意先名・仕入先名等は架空データの想定。実在の個人情報を入れられて
  しまう余地があるかも確認）、ある場合の保存・削除手段
- 可用性：大量データ・深いBOM・巨大ステップ数でのメモリ/CPU消費上限、重い計算（MRP展開・能力山積み等）が
  UIスレッドを長時間ブロックしないか（Web Worker化の要否）、無限ループ・再帰の上限
- エラー処理：例外時に白画面にならない（Error Boundaryの有無。現状未導入の可能性があるため確認）、
  詳細なスタックトレースを利用者に見せない
- 外部サービス依存がある場合の障害時の挙動（現状は無い想定）

### 認証認可・監査
- 現状のアプリに認証認可・監査が必要な機能があるかを判定し、該当なしの場合は理由を記録する
  （前提のとおりバックエンドが無いため、原則として該当なしになる見込み）

**将来バックエンド/SSO導入時のチェック観点**（現時点では実装せず、導入時に検討するための備忘）：
  - 権限チェックがクライアント側のみになっていないこと（サーバー側での再検証が必須）
  - セッション/トークンの保管方式（HttpOnly Cookieを優先し、localStorage/sessionStorageへの
    トークン保存を避ける）
  - CSRF対策（SameSite Cookie、CSRFトークン等）
  - 操作の監査ログ（誰が・いつ・何をしたか）の記録と改ざん耐性
  - ログへの機密（パスワード・トークン・個人情報）非出力

## レビュー結果の記録形式

`docs/security/reports/review-YYYYMMDD-HHMM.md`に、以下を出力する。

- サマリ：検査範囲、コミットSHA、重大度別の件数
- 指摘一覧（各指摘に必須の項目）：
  - ID（`SEC-001`）、重大度（Critical/High/Medium/Low/Info）、カテゴリ（本書の項目名）
  - 該当箇所（`ファイル:行`）、根拠、影響、修正案
  - 対応するテスト（追加したテストファイル名とテスト名）または「テスト不能の理由」
- 該当なしとした項目と、その理由
- テスト実行結果（成功/失敗数、失敗の内訳）
