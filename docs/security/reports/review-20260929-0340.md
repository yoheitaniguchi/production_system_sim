### SEC-001（Medium）CSV数式インジェクション（CSVエクスポート）

- カテゴリ：§6.1 インジェクション・XSS／入力検証
- 該当箇所：`src/csvExport.ts:6-12`（`escapeCsvField`）。到達経路の例：
  `src/components/CostPanel.tsx:45,54`（`itemName(c.itemId)`をCSVセルへ出力）
- 根拠：`escapeCsvField`はカンマ・引用符・改行のみをエスケープし、セル先頭が`=`/`+`/`-`/`@`の場合に
  Excel・Google Sheets等が数式として評価してしまう「CSV数式インジェクション」への対策が無い。
  `masterData.ts`の品目名（`name`）・作業区コード等はユーザーが自由な文字列を設定でき
  （書式制限を確認したが無い）、`CostPanel.tsx`のCSVエクスポートでその値がそのままセルに載る
- 影響：悪意ある（またはいたずらの）品目名を設定した状態でCSVを出力し、それを別の利用者が
  Excel等で開いた場合、埋め込まれた数式が実行される（例：外部URLへの自動アクセス、旧バージョンの
  Excelでは`DDE`経由のコマンド実行）。本アプリは教材用で共有・配布されるCSVが想定される用途のため、
  実際に到達可能と判断した
- 修正案：`escapeCsvField`で、フィールドの最初の文字が`=`・`+`・`-`・`@`・タブ・CR の場合、
  先頭に無害化のための`'`（シングルクォート）を1文字だけ挿入してから既存のエスケープ処理を適用する
  ```diff
   function escapeCsvField(field: string | number): string {
     const text = String(field);
  -  if (/[",\r\n]/.test(text)) {
  -    return `"${text.replace(/"/g, '""')}"`;
  -  }
  -  return text;
  +  const neutralized = /^[=+\-@\t\r]/.test(text) ? `'${text}` : text;
  +  if (/[",\r\n]/.test(neutralized)) {
  +    return `"${neutralized.replace(/"/g, '""')}"`;
  +  }
  +  return neutralized;
   }
  ```
- 対応するテスト：`src/csvExport.security.test.ts`（`[@security]`）
  「セル先頭が=/+/-/@の場合は数式として評価されないよう無害化される」×4、
  「数式を意図しない通常の品目名はこれまでどおり変化しない」×1（回帰確認）
- 実行結果：4件失敗（脆弱性の顕在化を確認）・1件成功

### SEC-002（Low）シナリオJSONインポートで未知キーが素通りする（プロトタイプ汚染への防御不足）

- カテゴリ：§6.1 入力検証・データ取り込み（プロトタイプ汚染）
- 該当箇所：`src/domain/scenarioIO.ts:216-242`（`collectSchemaErrors`）・`scenarioIO.ts:343`
  （`const state = raw.state as unknown as SimulationState;`）
- 根拠：`collectSchemaErrors`は`TABLE_SPECS`で宣言された既知フィールドの型のみを検査し、行や
  最上位`state`オブジェクトに付いた「未知の余分なキー」（`__proto__`という名前のキーを含む）を
  拒否も除去もしない。戻り値も`raw.state`（`JSON.parse`結果そのもの）を型アサーションで
  すり抜けさせているだけで、`masterIO.ts`の`parseMasterSnapshot`（フィールドを個別に取り出して
  新規オブジェクトを組み立てる安全な作り）と異なり、素通りする
- 影響：現時点のリポジトリ全体を`grep`で確認した限り、パース結果を`Object.assign`や`for...in`で
  別オブジェクトへ書き写すコードは存在せず（0件）、`reducer.ts`の`SCENARIO_IMPORT`は
  `structuredClone(action.payload.state)`のみを行う（`structuredClone`は`__proto__`という名前の
  own propertyを「定義」として複製するため、実際にAgent`Object.prototype`を汚染する経路には
  ならない）。したがって**今日時点で実際にプロトタイプ汚染に至る経路は確認できなかった**。
  影響は「将来Object.assign/for-in等でこの値を書き写すコードが追加された場合の保険が無い」という
  多層防御の欠落であり、悪用可能性を断定できないためLowとした（Highへ引き上げる推測はしない）
- 修正案：`collectSchemaErrors`に、各行・最上位stateオブジェクトについて「`TABLE_SPECS`（および
  `day`・`SEQUENCES`）で宣言されたキー以外が存在しないこと」を検査する処理を追加し、余分なキーが
  あれば（`__proto__`・`constructor`・`prototype`に限らず）エラーとして拒否する
- 対応するテスト：`src/domain/scenarioIO.security.test.ts`（`[@security]`）
  「最上位stateに__proto__という名前の余分なキーがあると取り込みを拒否する」、
  「行オブジェクトに未知の余分なキーがあると取り込みを拒否する」（業務ルール由来の失敗でないことを
  クリーンな比較対照で確認済み）、「未知キーの無い正規のシナリオは引き続き取り込める」（回帰確認）
- 実行結果：2件失敗（指摘の顕在化を確認）・1件成功

### SEC-003（Low）Error Boundary未導入＋localStorageアクセス未保護による白画面

- カテゴリ：§6.3 ログ・個人情報・可用性（エラー処理）／§6.1 ブラウザストレージ・状態管理
- 該当箇所：`src/theme.ts:31-37`（`loadStoredTheme`）・`src/App.tsx:51`
  （`useState<string>(() => loadStoredTheme())`）・`src/main.tsx`（Error Boundaryが1つも無い）
- 根拠：`loadStoredTheme()`は`window.localStorage.getItem()`をtry/catchで保護しておらず、
  `App`コンポーネントの初回描画時（`useState`の初期化関数）に直接呼ばれる。かつ本アプリには
  `componentDidCatch`/`getDerivedStateFromError`によるError Boundaryが1つも無い
  （`grep`で確認：0件）。Playwrightで実際にブラウザ上で検証した結果、`window.localStorage`への
  アクセス自体が例外を投げる状況（プライバシー設定・一部ブラウザの設定・組織のポリシー等で
  発生しうる）を再現すると、`<body>`のinnerTextが空（真っ白）のまま復旧手段なく固まることを
  確認した
- 影響：教材として研修環境（学校・企業のPC）で使われる想定であり、そうした環境ではプライバシー
  設定やブラウザ拡張機能でストレージアクセスが制限されている場合がある。発生すると、エラー
  メッセージも再読み込みの導線も無いまま操作不能になる
- 修正案：
  1. `theme.ts`の`loadStoredTheme()`をtry/catchで囲み、例外時は`DEFAULT_LIGHT_THEME_ID`相当へ
     フォールバックする（`storeTheme()`側も同様に保護する）
  2. `App`コンポーネントをトップレベルのError Boundary（`src/components/ErrorBoundary.tsx`を新設）で
     包み、予期しない例外発生時にも「エラーが発生しました。再読み込みしてください」のような
     最低限の回復導線を表示する
- 対応するテスト：`e2e/security.spec.ts`（`[@security]`）
  「localStorageへのアクセスが例外を投げても、白画面のまま固まらない」
- 実行結果：1件失敗（脆弱性の顕在化を、実ブラウザ上で確認済み）

### SEC-004（Low）`.gitignore`に`.env*`の除外が無い

- カテゴリ：§6.3 シークレット・設定不備
- 該当箇所：`.gitignore`（全体）
- 根拠：`.gitignore`には`node_modules`・`dist`・Playwright/ESLint/vitest関連の除外はあるが、

- 影響：現時点で本リポジトリは`VITE_`環境変数や`.env`ファイルを一切使用していない（`grep`で

  ```diff
  +# 環境変数（現状未使用だが、将来の誤コミット防止）
  +.env
  +.env.*
  +!.env.example
  ```
- 対応するテスト：`security/dependencies.security.test.ts`（`[@security]`）
  「.env*パターンが除外されている」
- 実行結果：1件失敗（指摘の顕在化を確認）

### SEC-005（Low）サードパーティGitHub ActionsがコミットSHA固定されていない

- カテゴリ：§6.3 シークレット・設定不備（サプライチェーン）
- 該当箇所：`.github/workflows/deploy.yml`（`peaceiris/actions-gh-pages@v4`）、
  `.github/workflows/pr-preview.yml`（`rossjrw/pr-preview-action@v1`）
- 根拠：両ワークフローとも`contents: write`（`pr-preview.yml`はさらに`pull-requests: write`）という
  強い`GITHUB_TOKEN`権限を持つ一方、使用しているサードパーティ製Actionはバージョンタグ参照のままで、
  コミットSHAに固定されていない（`actions/checkout`等のGitHub公式Actionは対象外とした）
- 影響：該当タグの指す内容が後から差し替えられた場合（タグの再作成、パッケージの乗っ取り等の
  サプライチェーン攻撃）、次回のワークフロー実行で任意のコードが強い権限のトークンとともに
  実行されてしまう。現時点で該当リポジトリ・タグの侵害は確認されていない（未確認）ため、
  到達可能性は理論上のものとしてLowとした
- 修正案：両Actionの参照を、現在のリリースタグが指す時点のコミットSHAに固定する
  （例：`uses: peaceiris/actions-gh-pages@<40桁SHA> # v4.x.x`のようにコメントでバージョンを併記）。
  依存関係のバージョン変更を伴わないため大きな変更ではないが、ワークフローファイルの変更のため
  §10の方針どおり事前承認を得てから行う
- 対応するテスト：`security/ci-workflows.security.test.ts`（`[@security]`）
  「(各ワークフローファイル)が参照するサードパーティActionはコミットSHAで固定されている」
- 実行結果：`deploy.yml`・`pr-preview.yml`で失敗（指摘の顕在化を確認）。`test.yml`・
  `flaky-check.yml`はサードパーティAction不使用のため成功

  `vite`→`esbuild`の開発サーバー任意リクエスト転送、いずれもテスト・ビルドツールチェーン専用）
