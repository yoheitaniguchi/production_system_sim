## 1. 総評

機械による検証（lint・型チェック・vitest約300件・a11y・業務シナリオE2E・依存脆弱性ゲート）とCI/CDはPoCとしては十分以上に
整っており、テストもピラミッド型に保たれている。一方、**「何を確かめるためのPoCか／いつ終えるか」が定義されておらず**、
次の一手が決まらない状態（`CLAUDE.md`「次の一手は特に決まっていない」）が生じている。また、コード・テスト・レビューの大半を
AIエージェントが担う中で、**人のレビューとマージの関門が実質的に機能していない証跡**（PR作成から1〜2分でのマージが多数）がある。
最優先は、①PoC定義（目的・出口基準）の明文化、②`main`のブランチ保護と人の責任範囲の明確化、③非機能目標の数値化の3点。
あわせて、`CLAUDE.md`が実装履歴の記録を兼ねて肥大化している点（文書の二重管理）と、1件ごとに重い11工程のフローを
変更規模に応じて軽くする余地がある点を中優先で指摘する。

## 3. 指摘事項（優先度順）

### [優先度：高] D-5・E-9 AI生成コードに対する人のレビュー・マージの関門が実質的に機能していない（要注意パターン2・6）

- 現状：
  - 実装・テスト・計画レビュー・実装レビューのほぼすべてをAI（Claude Code本体と`.claude/agents/`配下の5サブエージェント）が担う
    （`docs/issue-workflow.md` §2の工程表で「担当：ユーザー」は承認ゲート〔#3〕とマージ〔#11〕のみ）。
  - 直近のPRは作成からマージまでが極端に短い：#104（79秒）、#114（85秒）、#116（105秒）、#108（117秒）、#117（96秒）、
    #111（82秒）。#116は727行・10ファイル、#114は858行・8ファイルの差分であり、人が差分を読んだとは考えにくい。
  - CIの完了を待たずにマージされている可能性が高い（`a11y`・`e2e-scenario`はPlaywrightのインストールを含み、数分かかる）。
  - `main`のブランチ保護（必須チェック・必須レビュー）の設定はリポジトリから確認できない（→質問1）。
  - 人のレビュー観点は`docs/issue-workflow.md` §10.3で定義されたばかり（PR #119、2026-10-07）で、運用実績はまだ無い。
- 問題：
  - 「AIレビュアーが通した＝正しい」となっており、AIがコードとテストの両方を書く場合に起きる「誤ったコードの挙動を
    テストの期待値にしてしまう」問題（`docs/test-process-standard.md` §4.7の注意書き）を、人が止める機会が無い。
  - CIがredのまま`main`に入ると、`deploy.yml`で公開版（教材）にそのまま配信される。
  - 誰が成果物に責任を持つのかが文書に書かれていない。
- 改善案：
  1. **最初の一手**：`main`にブランチ保護（Rulesetsでも可）を設定し、`Test / test`・`Test / a11y`・`Test / e2e-scenario`を
     必須ステータスチェックにする。個人開発で承認者が自分しかいない場合、「必須レビュー」は付けず、必須チェックだけでも
     「CI red のままマージ」は機械的に防げる。
  2. `docs/process/dod.md`（下記C-2）に「**AI生成物の責任者はマージした人**。マージ前に人が確認する最小範囲」を明記する。
     全行を読むのではなく、人の確認は判断の妥当性に絞る：
     - 受け入れ条件と、それを保証するテストの**期待値**が仕様（`v5-spec.md`／Issue）から来ているか（コードから逆算していないか）
     - `docs/design.md` §3（EXT-xx）に追加された解釈・決定の妥当性
     - PRプレビューでの主要操作の目視
  3. PRテンプレートに「人が確認した点」欄と「AI生成コードを含む場合、上記の範囲を確認した」チェックを追加する（D-2）。
- Good / Bad：
  - ❌ AIがコード・テスト・レビューを行い、CI完了前に1分でマージする
  - ✅ CIの必須チェックが通るまでマージボタンが押せず、人は期待値と設計判断だけを見て承認する

### [優先度：高] A-1〜A-5 PoCの目的・成功／撤退基準・期限・本番化方針が定義されていない（要注意パターン1関連）

- 現状：
  - `README.md`・`CLAUDE.md`の冒頭は「何を作るか」（生産管理のドメイン連携を学ぶためのシミュレーター、対象読者は開発チームメンバー、
    商用製品ではなく教材）であり、「何を確かめるか」（仮説）・成功基準・期限が無い。
  - `CLAUDE.md`「次にやるべきこと」は「次の一手は特に決まっていない」「着手前にユーザーに優先順位を確認すること」で終わっており、
    残りのIssue 5件は判断待ち。出口が無いため、機能追加（#51〜#67の15件超）が続いている。
  - 「本番化」に相当する方針（教材として研修で使い続けるのか、自動テスト管理アプリ等の別PoCの題材に転用するのか）が文書に無い。
  - 検証しなかった範囲は個別の記述（例：`CLAUDE.md`「他4テーマは今回検証対象外」、design.md §9.8「残存する簡略化・限界」）に
    散在し、まとまった一覧が無い（A-5は⚠️）。
- 問題：
  - 何ができたら終わりか判定できないため、優先順位がその都度の思いつきになり、費用対効果の判断（`CLAUDE.md`の表）も
    「何に対しての効果か」が不明確になる。
  - 研修利用など教材の利用者に触らせる段階に移ったとき、何を検証済みで何が未検証かを説明できない。
- 改善案：
  1. **最初の一手**：付録の雛形で`docs/process/poc-definition.md`を作る。本プロジェクト向けの記入例（ユーザーの確認が必要。→質問2）：
     - 検証したい仮説：「受注→MRP→購買・製造→出荷の伝播を操作しながら追えると、開発メンバーが生産管理のドメイン連携を
       短時間で理解できる」「AI駆動＋機械検証中心のプロセスで、仕様準拠の業務ロジックを小さなチームで維持できる」
     - 成功基準（例）：開発メンバーN名がTC-01〜18の演習を演習ガイドだけで完走し、事後確認テストで正答率80%以上
     - 撤退・終了基準（例）：期限までに上記を満たさない場合は機能追加を止め、学びを報告書にまとめて終了
     - 期限：例）2026年12月末
     - 検証しない範囲：性能（大規模データ）、複数ブラウザ、永続化、マルチユーザー、本番運用（監視等）
     - 本番化の方針：研修で継続利用するなら「引き継ぐ」、別製品化するなら「作り直す」を決める期限を書く
  2. `CLAUDE.md`「次にやるべきこと」の表は、PoC定義の成功基準に寄与するかどうかで並べ直す。
  3. 「検証しない範囲」はPoC定義書の1か所に集約し、各所の記述からはそこへリンクする（B-6と同じ考え方）。

### [優先度：高] F-3・F-6 非機能の目標が数値で定義されていない（要注意パターン4）

- 現状：
  - `docs/test-process-standard.md` 付録Cに非機能目標の「チェックリストと例」はあるが、値は例示のままで確定していない。
  - `docs/report/poc-readiness-report.md` 調査項目5も「対応ブラウザ・画面サイズ・研修利用法についての数値目標の記述は見つからず」。
  - 実際に検証している非機能は、アクセシビリティ（axe-coreのcritical/serious 0件、CIで自動）とセキュリティ（本番依存のhigh/critical
    脆弱性0件）のみで、これらは基準が明確（✅相当）。
- 問題：
  - マスタを自由に登録できる（4階層BOM・自転車プリセット）ため、MRP展開・山積み計算の計算量はデータ次第で増える。基準が無いと
    「遅い」と感じた時に直すべきか判断できない。
  - 研修で使うブラウザ・画面幅が決まっていないため、E2E（Chromiumのみ）の妥当性も判断できない。
- 改善案：
  1. **最初の一手**：PoC定義書の「非機能の検証範囲」に、付録Cの7項目のうち本PoCで扱うものだけ値を確定して書く。教材・単一ブラウザ・
     バックエンド無しの前提で、最低限次の3つで足りる：
     - 性能（計算）：例）既定プリセット＋受注20件でMRP実行が1秒以内、4階層BOM×品目100件で3秒以内
     - 構成：例）Chrome／Edgeの最新版、横幅1366px以上
     - ユーザビリティ：例）演習シナリオ完走率（A-1の成功基準と共通化）
  2. 性能は`src/domain/`が純粋関数であることを活かし、vitestで大きめのマスタを生成して`runMRP()`の実行時間を計測する
     ベンチマークを1本だけ用意する（F-4。CIでは閾値を緩めに設定し、劣化検知に使う）。
  3. 扱わない項目（ロングラン・ストレス等）は「検証しない範囲」として明記する。

### [優先度：中] C-1・D-1・プロセスの重さ 1件ごとに11工程・AIレビュー延べ6回のフローが、PoCの「早く学ぶ」に対して重い

- 現状：
  - `docs/issue-workflow.md`は全変更（typo除く）に、Issue下書き→仕様レビュー→承認→下書きPR→計画レビュー3観点→実装→
    実装レビュー3観点→PRレビュー（AI＋人）→マージの11工程を求める（PR #119で導入、運用実績はまだ無い）。
  - 一方でPR差分は大きめ：#118が1,322行・26ファイル、#114が858行、#116が727行。
- 問題：
  - 工程は多いのに、人が実際に関与する時間は短い（D-5参照）。AIの工程を増やしても、人の判断が入る点が増えるわけではない。
  - 機能の大小に関わらず同じ工程を踏むと、小さな改善を試して学ぶ速度が落ちる。
- 改善案：
  1. 変更規模で2つの経路に分ける（`docs/issue-workflow.md`に追記）。例：
     - **軽量経路**：差分300行未満、かつ`src/domain/`のロジック変更や依存追加・CI変更が無いもの → 計画レビューを省略し、
       実装レビューは該当観点1つ、PRレビューは`/code-review`＋人の確認（D-5の最小範囲）のみ
     - **標準経路**：上記以外 → 現行のフロー
  2. 差分が500行を超える見込みのIssueは、計画段階で分割を検討する（例：#118はレビュー基盤の構築と指摘対応を分けられた）。
  3. 新フローを最初のIssue数件に適用した後、C-3の振り返りで工程ごとに「指摘を出したか」を見て、効果の無い工程を削る。

### [優先度：中] F-1・F-2 セキュリティは充実しているが、シークレット検知と依存更新の自動化が無い

- 現状：
  - 設計時の確認：PR #119で計画レビューに`security-reviewer`を組み込んだ（運用実績はまだ無い）。
  - CIでの検証：ESLint、`@security`タグ付きテスト（`security/dependencies.security.test.ts`がvitest内で`npm audit --omit=dev`を実行し
    high/critical 0件を検証、`security/ci-workflows.security.test.ts`がサードパーティActionのSHA固定を検証）。
  - シークレット検知（gitleaks／GitHub Secret Scanning）・依存の自動更新（Dependabot）の設定はリポジトリ内に無い。
- 問題：
  - `npm audit`をネットワーク依存のまま単体テストの中で実行しているため、レジストリ障害で`test`ジョブが落ちる（単体テストの安定性と混ざる）。

- 改善案：
  1. `.github/dependabot.yml`を追加し、npmとGitHub Actionsを週1で更新提案させる（Actionsの更新はSHA固定と両立する）。
  2. リポジトリ設定でSecret Scanning（公開リポジトリなら無料）を有効化する（→質問4）。
  3. `npm audit`はvitestから分離し、`test.yml`に`npm run audit:security`の独立ステップ（または独立ジョブ）として置く。
