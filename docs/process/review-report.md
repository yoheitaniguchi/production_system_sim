## 1. 総評

機械による検証（lint・型チェック・vitest約300件・a11y・業務シナリオE2E・依存脆弱性ゲート）とCI/CDはPoCとしては十分以上に
整っており、テストもピラミッド型に保たれている。一方、**`main`にブランチ保護が無く、CIの完了前に（意図せず）マージされている**ため、
整っている機械検証がマージの関門として働いていない。また、PoCの目的は「生産管理システムの構想検証」「AI駆動開発プロセスの検証」
「テスト管理アプリの構想検証」の3つと回答を得たが、**どれもリポジトリに書かれておらず、仮説・判定基準・反復の区切りが無い**ため、
次の一手が決まらない状態（`CLAUDE.md`「次の一手は特に決まっていない」）が生じている。
最優先は、①ブランチ保護による必須チェック化（設定のみで即日可能）、②3つの目的それぞれの仮説と判定方法を書いたPoC定義と、
全体期限の代わりの「反復ごとのタイムボックス」、③非機能目標の数値化の3点。
あわせて、`CLAUDE.md`が実装履歴の記録を兼ねて肥大化している点（文書の二重管理）と、1件ごとに重い11工程のフローを
変更規模に応じて軽くする余地がある点を中優先で指摘する。

## 3. 指摘事項（優先度順）

### [優先度：高] D-5・E-9 AI生成コードに対する人のレビュー・マージの関門が実質的に機能していない（要注意パターン2・6）

- 現状：
  - 実装・テスト・計画レビュー・実装レビューのほぼすべてをAI（Claude Code本体と`.claude/agents/`配下の5サブエージェント）が担う
    （`docs/issue-workflow.md` §2の工程表で「担当：ユーザー」は承認ゲート〔#3〕とマージ〔#11〕のみ）。
  - 直近のPRは作成からマージまでが極端に短い：#104（79秒）、#114（85秒）、#116（105秒）、#108（117秒）、#117（96秒）、
    #111（82秒）。#116は727行・10ファイル、#114は858行・8ファイルの差分であり、人が差分を読んだとは考えにくい。
  - CIの完了を待たずにマージされている可能性がある。本PR（#122）の実績で、`e2e-scenario`ジョブはブラウザのキャッシュが無い初回で
    約5分16秒、キャッシュが効いた2回目で約41秒、`a11y`ジョブは約45〜60秒かかった。79〜117秒でのマージは、キャッシュが無い場合は
    確実にCI完了前、キャッシュが効いた場合でも完了とほぼ同時かその前であり、少なくとも結果を確認する時間は取れていない
    （各PRの実際の完了時刻との突き合わせは未実施）。いずれにせよ、CI完了前のマージを防ぐ仕組みが無いことは確かで、
    ユーザー回答により、CI完了前のマージは**意図しない運用**と確認した。
  - `main`にブランチ保護は**設定されていない**（ユーザー回答）。
  - 人のレビュー観点は`docs/issue-workflow.md` §10.3で定義されたばかり（PR #119、2026-10-07）で、運用実績はまだ無い。
- 問題：
  - 「AIレビュアーが通した＝正しい」となっており、AIがコードとテストの両方を書く場合に起きる「誤ったコードの挙動を
    テストの期待値にしてしまう」問題（`docs/test-process-standard.md` §4.7の注意書き）を、人が止める機会が無い。
  - CIがredのまま`main`に入ると、`deploy.yml`で公開版（教材）にそのまま配信される。
  - 誰が成果物に責任を持つのかが文書に書かれていない。
- 改善案：
  1. **最初の一手**：`main`にRuleset（Settings → Rules → Rulesets → New branch ruleset）を設定する。設定値の案：
     - 対象：Default branch
     - Require a pull request before merging：ON（必要な承認数は**0**。開発者が1名のみで、自分のPRは自分で承認できないため）
     - Require status checks to pass：ON。必須チェックに`test`・`a11y`・`e2e-scenario`を指定（`preview`は任意）。
       「Require branches to be up to date before merging」はOFFでよい（1人開発で頻繁な再実行を避ける）
     - Block force pushes：ON／Restrict deletions：ON
     - Bypass list：空（リポジトリ管理者も迂回しない。緊急時はRulesetを一時的に無効化する）
     これで「CI完了前・CI redのままマージ」がボタン操作上できなくなる。リポジトリは公開のため、Rulesetsは無料プランでも使える。
  2. `docs/process/dod.md`（下記C-2）に「**AI生成物の責任者はマージした人**。マージ前に人が確認する最小範囲」を明記する。
     全行を読むのではなく、人の確認は判断の妥当性に絞る：
     - 受け入れ条件と、それを保証するテストの**期待値**が仕様（`v5-spec.md`／Issue）から来ているか（コードから逆算していないか）
     - `docs/design.md` §3（EXT-xx）に追加された解釈・決定の妥当性
     - PRプレビューでの主要操作の目視
  3. PRテンプレートに「人が確認した点」欄と「AI生成コードを含む場合、上記の範囲を確認した」チェックを追加する（D-2）。
- Good / Bad：
  - ❌ AIがコード・テスト・レビューを行い、CI完了前に1分でマージする
  - ✅ CIの必須チェックが通るまでマージボタンが押せず、人は期待値と設計判断だけを見て承認する

### [優先度：高] A-1〜A-5 PoCの目的・判定基準・反復の区切り・本番化方針がリポジトリに書かれていない（要注意パターン1関連）

- 現状：
  - `README.md`・`CLAUDE.md`の冒頭は「何を作るか」（生産管理のドメイン連携を学ぶためのシミュレーター、商用製品ではなく教材）であり、
    「何を確かめるか」（仮説）・判定基準が無い。
  - ユーザー回答により、PoCの目的は次の3つと確認した：①生産管理システムの構想検証、②AI駆動開発プロセスの検証、
    ③テスト管理アプリの構想検証。全体の期限は設けず、「検証して必要な要件を構想し、実装・検証を繰り返す」ことを目的とする。
    ただし、いずれもリポジトリ上の文書には書かれていない（README・CLAUDE.mdは「教材」と説明しており、回答と食い違っている）。
  - `CLAUDE.md`「次にやるべきこと」は「次の一手は特に決まっていない」で終わっており、残りのIssue 5件は判断待ち。
  - 検証しなかった範囲は個別の記述（例：`CLAUDE.md`「他4テーマは今回検証対象外」、design.md §9.8「残存する簡略化・限界」）に
    散在し、まとまった一覧が無い（A-5は⚠️）。
- 問題：
  - 全体の期限を置かない継続的な構想検証という進め方自体は妥当だが、**反復ごとの問いと区切りが無い**と、「機能を足すこと」が目的化する。
    実際、#51〜#67の15件超の機能追加は、どの目的のどの問いに答えたのかが記録されていない。
  - ①の構想検証の成果（「生産管理システムにはこの要件が必要／不要と分かった」）が、コードとIssueに埋もれて取り出せない。
  - ②のAI駆動開発プロセスの検証は、今回の指摘（CI完了前のマージ等）のような**プロセス上の観察そのものが成果**だが、記録先が無い。
- 改善案：
  1. **最初の一手**：付録の雛形を元に`docs/process/poc-definition.md`を作る。全体期限の欄は「設けない（継続的な構想検証）」と明記し、
     代わりに目的ごとの仮説・判定方法と、反復のタイムボックスを書く。記入案：

     | 目的 | 検証したい仮説（例） | 判定方法（例） |
     |---|---|---|
     | ①生産管理システムの構想検証 | 受注〜出荷の7ドメイン連携を動かして確かめると、本番システムに必要な要件（MRP・工程・ペギング・原価・能力等）の要否と優先度を判断できる | 反復ごとに「要件の要否が判明した論点」を1件以上`docs/process/findings.md`に記録できたか |
     | ②AI駆動開発プロセスの検証 | 人が要件と判断に集中し、実装・テスト・レビューをAIと機械検証に任せても、仕様準拠の品質を保てる | 反復ごとに、マージ後に見つかった不具合件数・CI red件数・人の確認に要した時間を記録し、推移を見る |
     | ③テスト管理アプリの構想検証 | CIのテスト結果（JUnit・カバレッジ・要件タグ）を集約すれば、要件ごとのテスト網羅状況を機械的に把握できる | `docs/test-management-app-requirements.md`の要件のうち、本リポジトリのデータで成立を確認できた割合 |

  2. **全体期限の代わりの区切り**：2週間を1反復とし、反復の開始時に「今回答える問い（上表の仮説のどれか）」と対象Issueを決め、
     終了時に結果（分かったこと・分からなかったこと）を記録する（C-3の振り返りと同じ場で行う）。
  3. **本番化の方針**：「このリポジトリのコードは本番化しない（本番の生産管理システムを作る場合は作り直す）。引き継ぐのは要件・構想と
     テストの考え方」と明記する。構想検証が目的であれば、これが最も事故の起きにくい既定値である。
  4. `README.md`・`CLAUDE.md`冒頭の「教材」という説明を、3つの目的に合わせて更新する。
  5. 「検証しない範囲」はPoC定義書の1か所に集約し、各所の記述からはそこへリンクする（B-6と同じ考え方）。

### [優先度：高] F-3・F-6 非機能の目標が数値で定義されていない（要注意パターン4）

- 現状：
  - `docs/test-process-standard.md` 付録Cに非機能目標の「チェックリストと例」はあるが、値は例示のままで確定していない。
  - `docs/report/poc-readiness-report.md` 調査項目5も「対応ブラウザ・画面サイズ・研修利用法についての数値目標の記述は見つからず」。
  - 実際に検証している非機能は、アクセシビリティ（axe-coreのcritical/serious 0件、CIで自動）とセキュリティ（本番依存のhigh/critical
    脆弱性0件）のみで、これらは基準が明確（✅相当）。
- 問題：
  - マスタを自由に登録できる（4階層BOM・自転車プリセット）ため、MRP展開・山積み計算の計算量はデータ次第で増える。基準が無いと
    「遅い」と感じた時に直すべきか判断できない。
  - 研修で使うブラウザ・画面幅が決まっていないため、E2E（Chromiumのみ）の妥当性も判断できない。
- 改善案：
  1. **最初の一手**：PoC定義書の「非機能の検証範囲」に、付録Cの7項目のうち本PoCで扱うものだけ値を確定して書く。教材・単一ブラウザ・
     バックエンド無しの前提で、最低限次の3つで足りる：
     - 性能（計算）：例）既定プリセット＋受注20件でMRP実行が1秒以内、4階層BOM×品目100件で3秒以内
     - 構成：例）Chrome／Edgeの最新版、横幅1366px以上
     - ユーザビリティ：例）演習シナリオ完走率（A-1の成功基準と共通化）
  2. 性能は`src/domain/`が純粋関数であることを活かし、vitestで大きめのマスタを生成して`runMRP()`の実行時間を計測する
     ベンチマークを1本だけ用意する（F-4。CIでは閾値を緩めに設定し、劣化検知に使う）。
  3. 扱わない項目（ロングラン・ストレス等）は「検証しない範囲」として明記する。

### [優先度：中] C-1・D-1・プロセスの重さ 1件ごとに11工程・AIレビュー延べ6回のフローが、PoCの「早く学ぶ」に対して重い

- 現状：
  - `docs/issue-workflow.md`は全変更（typo除く）に、Issue下書き→仕様レビュー→承認→下書きPR→計画レビュー3観点→実装→
    実装レビュー3観点→PRレビュー（AI＋人）→マージの11工程を求める（PR #119で導入、運用実績はまだ無い）。
  - 一方でPR差分は大きめ：#118が1,322行・26ファイル、#114が858行、#116が727行。
- 問題：
  - 工程は多いのに、人が実際に関与する時間は短い（D-5参照）。AIの工程を増やしても、人の判断が入る点が増えるわけではない。
  - 機能の大小に関わらず同じ工程を踏むと、小さな改善を試して学ぶ速度が落ちる。
- 改善案：
  1. 変更規模で2つの経路に分ける（`docs/issue-workflow.md`に追記）。例：
     - **軽量経路**：差分300行未満、かつ`src/domain/`のロジック変更や依存追加・CI変更が無いもの → 計画レビューを省略し、
       実装レビューは該当観点1つ、PRレビューは`/code-review`＋人の確認（D-5の最小範囲）のみ
     - **標準経路**：上記以外 → 現行のフロー
  2. 差分が500行を超える見込みのIssueは、計画段階で分割を検討する（例：#118はレビュー基盤の構築と指摘対応を分けられた）。
  3. 新フローを最初のIssue数件に適用した後、C-3の振り返りで工程ごとに「指摘を出したか」を見て、効果の無い工程を削る。

### [優先度：中] C-3・C-4・F-5 振り返りと利用者からのフィードバックの記録が無い

- 現状：振り返りメモは見当たらない。試用はユーザー本人のみで、その記録はリポジトリ外にも無い（ユーザー回答）。UIの評価は
  `ux-reviewer`（AI）とaxe-coreに依存している。
- 問題：構想検証（目的①）では、ユーザー本人の試用で「何が分かったか」こそが主要な成果だが、記録が無いため残らない。
  AI駆動開発プロセスの検証（目的②）も、観察を記録しないと評価できない。
- 改善案：
  1. **最初の一手**：反復の区切り（2週間）ごとに`docs/process/retrospectives/YYYY-MM-DD.md`を1枚書く。項目は
     「今回の問い／分かったこと（目的①③）／プロセスの観察（目的②：CI red件数・マージ後の不具合・AIレビューが有効だった指摘）／
     Keep・Problem・Try」。Tryは次の反復でIssue化する。
  2. 本人の試用で気づいた点は、その場でIssue（ラベル例：`finding`）にするか`docs/process/findings.md`に1行で書く。
     試用者が本人のみである点は、PoC定義書の「検証しない範囲」に「第三者によるユーザビリティ評価」として明記する。

### [優先度：中] F-1・F-2 セキュリティは充実しているが、シークレット検知と依存更新の自動化が無い

- 現状：
  - 設計時の確認：PR #119で計画レビューに`security-reviewer`を組み込んだ（運用実績はまだ無い）。
  - CIでの検証：ESLint、`@security`タグ付きテスト（`security/dependencies.security.test.ts`がvitest内で`npm audit --omit=dev`を実行し
    high/critical 0件を検証、`security/ci-workflows.security.test.ts`がサードパーティActionのSHA固定を検証）。
  - シークレット検知（gitleaks／GitHub Secret Scanning）・依存の自動更新（Dependabot）の設定はリポジトリ内に無い。
- 問題：
  - `npm audit`をネットワーク依存のまま単体テストの中で実行しているため、レジストリ障害で`test`ジョブが落ちる（単体テストの安定性と混ざる）。
  - 依存の脆弱性は検知しても、更新は手作業になる。
- 改善案：
  1. `.github/dependabot.yml`を追加し、npmとGitHub Actionsを週1で更新提案させる（Actionsの更新はSHA固定と両立する）。
  2. 公開リポジトリのため無料で使える。Settings → Code security で Secret scanning と Push protection を有効化する
     （シークレットを含むpushをGitHub側で拒否できる）。あわせてCodeQL（default setup）も無料で有効化でき、SAST相当を追加できる。
  3. `npm audit`はvitestから分離し、`test.yml`に`npm run audit:security`の独立ステップ（または独立ジョブ）として置く。

### [優先度：低] B-3 設計判断はdesign.mdのEXT-xxで記録されているが、状態と棄却案が揃っていない

- 現状：`docs/design.md` §3のEXT-1〜42が「論点／v5の記述／追加決定」の表形式で判断理由を記録しており、実質的にADRとして機能している。
  ただし「検討して捨てた案」は一部（EXT-18・EXT-24等）にしか無く、後から覆った決定（例：EXT-24で断念したカスケード更新）の状態も表に無い。
- 改善案：新たに`docs/adr/`を作ると二重管理になるため作らない。EXT表に「状態（有効／廃止→EXT-xx）」と「棄却した案」の列を追加し、
  今後の追加分から記入する。

### [優先度：低] B-5・E-6 要件ID・工程タグの付与が途中

- 現状：`docs/test-tagging.md`の書式（`[UC-xx][工程][種類][観点]`）で、10ファイル・101件に工程タグが付与済み（単体81／結合18／総合2）。
  対象ファイルの残りは未付与。受け入れ条件→テストの対応はPRテンプレートの「受け入れ条件の充足」表で追えている（E-6は✅）。
- 改善案：残りのファイルへの付与を継続する。新規テストはタグ付きで書くことを`docs/process/dod.md`に入れる。

### [優先度：低] E-8 flakyの検知がvitestのみで、E2Eが対象外

- 現状：`.github/workflows/flaky-check.yml`は平日1回、`npm test`（vitest）を3回実行する。不安定になりやすいPlaywright（E2E・a11y）は対象外。
  失敗時の通知・Issue化の仕組みも無い。
- 改善案：`npx playwright test --repeat-each=3`のステップを追加し、失敗時はworkflowの失敗通知（GitHubのメール）で気づけることを確認する。
  純粋関数中心のvitestは本来flakyになりにくく、検知すべきはE2E側である。
