# PoC定義：生産管理シミュレーター

- 状態：確定（2026-10-08）
- 根拠：`docs/process/review-report.md` A-1〜A-5・F-3・F-6、および2026-10-07のユーザー回答
- 本書の位置付け：本リポジトリで「何を確かめるか」「どこまでやって何をやらないか」の正本。
  機能の優先順位（`CLAUDE.md`「次にやるべきこと」）は、本書の仮説に寄与するかどうかで判断する

## 1. 検証したい仮説

本PoCには3つの目的がある。全体の期限は設けず、「検証して必要な要件を構想し、実装・検証を繰り返す」ことを続ける。

| # | 目的 | 検証したい仮説 | 判定方法（反復ごとに記録する） |
|---|---|---|---|
| ① | 生産管理システムの構想検証 | 受注〜出荷の7ドメイン連携（MRP・工程・ペギング・原価・能力等）を動かして確かめると、本番の生産管理システムに必要な要件の要否と優先度を判断できる | 反復ごとに「要否が判明した要件の論点」を1件以上、`docs/process/findings.md`に記録できたか |
| ② | AI駆動開発プロセスの検証 | 人が要件と判断に集中し、実装・テスト・レビューをAIと機械検証に任せても、仕様に沿った品質を保てる | 反復ごとに、①マージ後に見つかった不具合の件数、②CIがredになった件数、③人の確認（`docs/process/dod.md` D7）にかかった時間の目安、を記録し推移を見る |
| ③ | テスト管理アプリの構想検証 | CIのテスト結果（JUnit・カバレッジ・要件タグ）を集約すれば、要件ごとのテストの網羅状況を機械的に把握できる | `docs/test-management-app-requirements.md`の要件のうち、本リポジトリのデータで成り立つと確認できたものの割合 |

## 2. 進め方（反復のタイムボックス）

- 全体の期限の代わりに、**2週間を1反復**とする
- 反復の開始時：1章の仮説のどれに答えるか（今回の問い）と、対象のIssueを決める
- 反復の終了時：`docs/process/retrospectives/YYYY-MM-DD.md`に次を記録する
  - 今回の問いと、分かったこと・分からなかったこと（目的①③）
  - プロセスの観察（目的②：1章の①〜③の数値、AIレビューが役に立った指摘・役に立たなかった工程）
  - Keep／Problem／Try（Tryは次の反復でIssue化する）
- 判定の結果、ある仮説が「成り立たない」と分かった場合は、それも成果として記録し、その目的の検証を終える

## 3. 本番化の方針

- **このリポジトリのコードは本番化しない。** 本番の生産管理システムやテスト管理アプリを作る場合は、作り直す
- 本番へ引き継ぐのは、要件・構想（`docs/process/findings.md`・`docs/design.md`）と、テストの考え方（`docs/test-process-standard.md`）
- 方針を変える（コードを引き継ぐ）場合は、その時点で本書を改訂し、5章の「検証しない範囲」を改めて検証計画に入れる

## 4. 非機能の目標値

`docs/test-process-standard.md` 付録Cの7項目のうち、本PoCで扱うものだけ値を決める（2026-10-08確定）。

| 項目 | 目標値 | 検証方法 | 現状 |
|---|---|---|---|
| 性能（計算） | 既定プリセット（木製イス）・受注20件でMRP実行が1秒以内。4階層BOM・品目100件で3秒以内 | vitestで大きめのマスタを生成し`runMRP()`の実行時間を計測するテストを追加する（レビューレポートF-4） | 未計測 |
| 構成 | Chromium系ブラウザ（Chrome・Edge）の最新版、横幅1366px以上 | CIのPlaywright（Chromium）で検証。他のブラウザは検証しない | CIで実施中 |
| アクセシビリティ | axe-coreのcritical／serious相当の違反0件（ライト・ダーク両テーマ×全タブ） | `npm run test:a11y`（CIの`a11y`ジョブ） | CIで実施中 |
| セキュリティ | 本番依存のhigh／critical脆弱性0件。シークレットをリポジトリに含めない | `npm run audit:security`、`@security`タグ付きテスト、GitHubのSecret scanning | 一部実施中（Secret scanningは設定待ち） |

## 5. 検証しない範囲

本PoCでは次を検証しない。本番化しない方針（3章）が前提であり、方針を変える場合は見直す。

| 範囲 | 理由・現状 |
|---|---|
| 第三者によるユーザビリティ評価 | 試用者は開発者本人のみ。本人の気づきは`findings.md`に記録する |
| 大量データでの性能（受注1万件など）・ストレス・ロングラン | 4章の性能目標の範囲を超える規模は扱わない |
| Chromium系以外のブラウザ（Firefox・Safari）、スマートフォン | 4章の構成のとおり |
| データの永続化・マルチユーザー・同時操作 | 永続化なし・単一セッションの設計（`CLAUDE.md`「技術スタック・アーキテクチャ」） |
| 本番運用（監視・バックアップ・障害対応） | バックエンドを持たない静的サイトで、本番化しないため |
| 6テーマのうち検証対象外の4テーマのコントラスト | a11y検査はライト（マテリアル・クリーン）・ダーク（ディープグレー）の2テーマのみ |
| v5-spec.mdの簡略化・限界として残した事項 | `docs/design.md` §9.8「残存する簡略化・限界」ほか、EXT-xxで対象外とした事項 |

## 6. 関係者

- 開発者・利用者・判断者：リポジトリのオーナー1名（委託先なし）
- AIエージェント（Claude Code とサブエージェント）は作業者であり、成果物の責任はマージする人が持つ（`docs/process/dod.md` D7）
