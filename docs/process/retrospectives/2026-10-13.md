## 4. Keep／Problem／Try

| 区分 | 内容 |
|---|---|
| Keep | 1項目＝1PRで小さく進め、各PRにCHANGELOGの追記と判定の更新を含めた（記録だけの別PRが無くなった） |
| Keep | セキュリティ上の修正は、テストで再現 → 人の承認 → 修正、の順を守った（#126） |
| Problem | 「人の確認時間」を測る仕組みが無く、目的②の指標が1つ欠けている → 振り返りの時点でユーザーが目安を答える運用で補う（下記Tryの判断） |
| Problem | 計画レビューの「省略」が続くと、省略の判断自体が確かめられない |
| Try（不採用） | PRテンプレートの「人の確認」欄に、かかった時間を書く欄を加える案は**採らない**（ユーザー判断：毎PRの記入は形骸化しやすいため）。代わりに、反復ごとの振り返りでユーザーが目安を答える |
| Try | 次の反復では、仮説①または③に答える機能開発を1件以上選び、`findings.md`に新しい記録を残す |
| Try | 軽量経路を実際に使い、省いた工程で見落としが出ないかを次回の振り返りで確かめる |
