# 生産管理ミニマムシミュレーター 設計書

**版数**: v1（v5仕様書 完全準拠版）
**目的**: 受注情報を入力すると、それが各ドメインへ伝播し出荷に至るまでの流れを、動くシミュレーターとして可視化する
**位置づけ**: 本書は `docs/v5-spec.md`（ユーザー提供「生産管理システム ミニチュア設計書 v5」、以下「v5仕様書」）を
実装仕様の一次資料とする**差分ドキュメント**である。v5仕様書が規定する業務ルール・データモデル・状態遷移・
中核ロジックの疑似コード・受入テストケースはそのまま採用し、本書には次の3種類の情報のみを記載する。

1. v5仕様書に対する**意図的な差分**（§2）
2. v5仕様書が**未規定・曖昧なまま残した点への追加決定**（§3）
3. 本プロジェクト固有の**実装方針**（データモデル対応・画面構成・アーキテクチャ・ディレクトリ構成、§4〜§8）

業務ルールの背景・根拠（なぜその機能が必要か、批判的レビューの経緯等）を確認したいときは `docs/v5-spec.md` を参照すること。

## 姉妹リポジトリ `mini-simulator` との関係

`mini-simulator`は小型コンベア装置（多階層BOM、即時発注トリガー、受注専属ペギングによる在庫モデル簡略化、
工程ステップを持たない3状態モデル）を題材にした簡易版を実装している。本リポジトリはそのアーキテクチャ
（React + TypeScript + Vite、バックエンドなし、`useReducer`による状態管理、ドメインロジックを純粋関数として
UIから独立させる設計、D0からの経過日数で日付を扱う等）を踏襲するが、`mini-simulator`とは**データモデル・
操作粒度の前提が異なる独立したプロジェクト**であり、`mini-simulator`のドメインロジック・型定義をそのまま
移植することはしない。詳細な差分は§2で述べる。

## §2 v5仕様書に対する意図的な差分

| # | 差分 | 内容 | 理由 |
|---|---|---|---|
| DEV-1 | PARTNERテーブルを統合しない | v5仕様書 §4は`PARTNER`（`partner_type`で顧客/仕入先を判別）に統合しているが、本実装では`Customer`/`Supplier`を別型として持つ（`mini-simulator`と同じ選択） | 型安全性・画面実装のしやすさを優先。実質的な差はテーブル数13→14のみで、業務ロジックへの影響はない |
| DEV-2 | 自動再生機能は実装しない | `mini-simulator`にある「次の日へ進む」を一定間隔で自動連打する機能は、Phase1では実装しない | §3で確定する通り、Phase1は工程着手/完了・入荷計上・出荷引当/実績・MRP実行・オーダ確定などが個別のユーザー操作になる。「日を進める」だけでは何も進行しなくなるため、自動連打の価値がほぼ失われる。操作が出揃った段階で改めて検討する |
| DEV-3 | 入荷・出荷の数量入力欄を持たない | v5データモデル（`received_qty`/`shipped_qty`の累積管理）は任意数量の分割対応が可能だが、本実装のUIでは**数量入力欄を設けず、1回の操作で「その時点で処理できる分すべて」を自動的に一括処理**する（入荷＝注文残全量、出荷＝受注残と出荷可能量の少ない方）。実装当初は「常に受注残＝発注残の全量を処理する」という誤った解釈で実装し、TC-15（不良により受注残10に対し出荷可能量が9しかないため9個だけ引き当てる）が成立しないことに気付いて修正した | ミニチュアとしてのUI複雑化（数量入力欄）を避けつつ、v5仕様書の受入テスト（TC-15など、出荷可能量が受注残に満たず自然に一部出荷になるケース）を正しく再現するため。データ型自体は将来任意数量を指定する分割対応を妨げない形で持つ |
| DEV-4 | 分析画面のうち「演習ガイド」（v5仕様書§8.1 D3）は先送り | KPIダッシュボード（D1）・ペギング追跡（D2）はPhase1に含めるが、§9のTCを画面上で自動判定・誘導する「演習ガイド」はPhase1.5以降とする | 実装コストが最も高く、`domain/*.test.ts`による自動テスト検証ループで仕様適合の確認はすでに担保できるため |

## §3 v5仕様書が未規定・曖昧なまま残した点への追加決定

| # | 論点 | v5仕様書の記述 | 追加決定 |
|---|---|---|---|
| EXT-1 | MRP展開時の需要処理順序 | `runMRP()`疑似コード（§7.1）の`demands`ループは処理順序を規定していない | **需要（`due`＝`confirm_day`）の昇順**にソートしてから`explode()`を呼ぶ。同着の場合は受注登録順（`so_no`昇順）とする。これにより複数受注が同一資材を取り合う際、納期が早い受注から優先的に供給量を消費する |
| EXT-2 | 受注取消時の関連オーダの扱い | §6.1のガード条件は「`shipped_qty == 0` かつ 確定オーダに紐付く実績が無い」とあるのみで、取消後にペグ先のMFG_ORDER/PURCHASE_ORDERをどう扱うかは無規定 | 取消操作の中で、`pegTo`鎖をたどり、**まだ実績（着手実績・入荷実績）が無いMFG_ORDER/PURCHASE_ORDERを連鎖的にCANCELED**へ遷移させる。放置すると「取消済受注のための製造/購買オーダ」という矛盾データが残るため |
| EXT-3 | 取消ガードの厳密な判定基準 | 「確定オーダに紐付く実績が無い」の"実績"の範囲が未定義 | **1件でも**次のいずれかに該当すれば取消不可とする二値判定にする：①ペグ先のいずれかのMFG_ORDERで`actual_start_day`が設定済みのWORK_INSTRUCTIONが存在する、②ペグ先のいずれかのPURCHASE_ORDERで`received_qty > 0`である。中間状態（一部の子オーダだけ実績あり）を許容せず、単純な有無判定に倒す |
| EXT-4 | 入荷計上のタイミング制約 | UC-11「入荷を計上する」に日付ガードの明記なし | 「入荷計上」操作は **`現在日 ≥ (confirm_day ?? due_day)`** の場合のみ実行可能とする。「今日発注していない材料が今日届かない」という因果律を維持するための追加ガード |
| EXT-5 | 出荷実績登録のタイミング制約 | 同上、出荷側は無規定 | ガードを設けない（早期出荷も許容）。納期遵守率KPIが結果として自然に反映するため、人為的な制約は不要と判断 |
| EXT-6 | MRP供給量計算におけるHOLD状態の扱い | §7.1 供給量初期化の`mfgOrders`条件は`status not in [DONE, CANCELED]`とあるのみで、`HOLD`（部品欠品で保留中）を含むかは記述上は含まれる（除外されていない）が明言はない | 字義通り**HOLDも供給に算入する**（除外リストに無いため）。部品欠品で止まっているだけで「作れる見込みがある仕掛残」として扱うのが一般的なMRPの考え方であり、v5の除外条件とも矛盾しない |
| EXT-7 | 納期回答（UC-05）の算出方法 | v5仕様書 §9.1のシーケンス図は「計画管理からの供給可能日」をMRP試算の結果として回答納期に反映する流れを示すが、§9.3の受入テスト表では**TC-03（納期回答）がTC-04（MRP実行）より先**に置かれており、両者の記述順序が矛盾する | シーケンス図側の「MRP試算に基づく自動ATP計算」は実装せず、**納期回答は人間（受注担当者）が希望納期を確認して確定するだけの単純操作**とする（デフォルト値として希望納期を表示し、そのまま確定するか、任意の値に変更して確定できる）。§9.3のTC順序（登録→回答→MRP実行）と整合させるための解釈 |
| EXT-8 | データ増分ログの表示フォーマット | §8.1は「どのテーブルに何行INSERT/UPDATEされたか」を要求するのみで、具体的な表示形式は無規定 | v5仕様書 §8.2のユースケース一覧の「主なデータ変更」列と同一の表記（例：`PLANNED_ORDER −5 / MFG_ORDER +2 / PURCHASE_ORDER +3 / WORK_INSTRUCTION +3`）をログの1行として、業務メッセージ（例：「計画オーダ5件を確定した」）と併記する |
| EXT-9 | 購買オーダの発注先（仕入先）の決め方 | `ITEM`マスタに仕入先を指す列が無く、`PARTNER`（仕入先）も対象品目を指す列を持たない。計画オーダ確定時にどの仕入先で`PURCHASE_ORDER`を起票するかが決定不能 | `ItemMaster`に`defaultSupplierId`（BUY品目のみ設定）を追加し、1品目＝1仕入先で固定する。複数仕入先からの選択・切替（v5仕様書 §5.2「仕入先の切替」が組織目線の判断として言及するもの）はPhase1のスコープ外とする |
| EXT-10 | HOLD状態からの具体的な復帰操作 | §6.3は「制約解消」でHOLD→WIPに戻るとあるのみで、契機となる操作が無い。§7.3 `completeStep()`疑似コードも、部品不足でHOLDにした後の`mo.status`をどう戻すか記述していない | 専用の「再試行」操作は設けない。HOLDになっても当該WORK_INSTRUCTIONの状態はWIPのまま変化しない（ガードは消費前に評価されるため）ため、**部品が充足した後に同じ「工程完了」操作（`WI_COMPLETE`）を同じ工程に対して再実行するだけで自然に成立する**。`completeStep()`側は、呼び出し時に`mo.status === HOLD`であれば処理開始時点で`WIP`に戻してから通常のガード評価を行う |
| EXT-11 | KPI「欠品発生件数」の算出元 | §10は「引当または出庫に失敗した回数」「引当・バックフラッシュの失敗ログ」とあるのみで、失敗イベントを蓄積する専用テーブルは定義していない | 専用の失敗ログテーブルは追加せず、**現在HOLD状態のMFG_ORDER数**を近似値として採用する（バックフラッシュの部品不足はHOLDという形で状態に残るため）。出荷引当の失敗は例外（`ShipmentError`）として即座に呼び出し側へ返るのみで状態に残らないため、この指標には含めない。より厳密な累積カウントが必要になった場合は、Phase 3のreducerで例外発生時にイベントログへ記録し、そこから集計する方式へ拡張する |
| EXT-12 | KPI「計画達成率」「直行率」の集計対象 | §10の定義はMFG_ORDER／WORK_INSTRUCTION全件を対象にしているように読めるが、TC-17の期待値（計画達成率90%・直行率90%）は、中間のサブアセンブリ（座面ASSY、完了時点でgood_qty10/plan_qty10=100%）まで含めて単純合算すると再現できない（含めると計画達成率95%になってしまう） | 両指標とも**末端の受注確定オーダ（`pegTo`が受注のペグキー"SO-xxx-n"形式、＝BOMレベル0）に限定**して集計する。計画達成率はそれらオーダのgood_qty/plan_qtyの合計比。直行率は各オーダについて「最終工程の良品数 ÷ 第1工程の投入数」（複数工程の歩留まりの掛け算に相当）を求め、オーダ横断で合算する。中間工程の出来高は含めない：組織目線のKPIとしても最終製品の顧客向け達成度を測るのが自然という判断 |
| EXT-13 | KPI「在庫回転」の分母（平均在庫数量）の扱い | §10の定義は「期間出庫数量 ÷ **平均在庫数量**」だが、時系列の在庫スナップショットを保持する仕組みは無く、平均値を算出できない | 平均在庫数量の代わりに**現在の総在庫数量**（全品目の`on_hand`合計）を分母として近似する。分母が0（在庫が無い、またはTC-17終了時点のようにすべて出荷・消費済みで手元在庫が無い）場合は`null`を返し、集計不能であることを明示する。より正確な期間平均が必要になった場合は、日次の在庫スナップショットを別途蓄積する仕組みが必要になる（Phase 3.5以降の課題） |
| EXT-14 | KPIダッシュボードの「両方」目線指標の配置 | §10の「主な目線」列は12指標中3指標（計画達成率・製造リードタイム実績・棚卸差異率）を「両方」に分類するが、design.md §5は画面構成を「組織目線/現場目線の別ブロック」の2ブロックとしており、「両方」指標をどちらに置くかは無規定 | どちらか一方に寄せると情報が欠落するため、**「両方」指標は組織目線・現場目線の両方のブロックに重複表示**する（`KpiDashboard.tsx`）。3ブロック目を新設せず、design.md §5の「2ブロック構成」という画面設計をそのまま維持しつつv5仕様書の目線分類を欠落なく反映するための判断 |

v5仕様書 §4 のER図をそのままTypeScriptの型定義に対応させる。命名は`camelCase`に変換し、日数フィールドは

### 在庫モデルについて

在庫（STOCK）は品目単位のfungibleな残高管理（`on_hand`／`allocated`）に統一し、ペギング（`peg_to`鎖）は
**追跡専用の別レイヤ**として物理在庫の取り合いには関与させない（v5仕様書 §7.4の設計判断そのもの）。
`mini-simulator`が採用している「仕掛品・完成品を受注ごとにペグして二値管理する」簡略化（受注専属の
MTOだから成立する簡略化）は、本プロジェクトでは採用しない。これはv5仕様書が明確に主張する標準的な
MRPの考え方（§7.1「有効在庫の式とMRPの正味所要計算の式は別物」）であり、教材としての難度は上がるが、
実務のMRPシステムにより近い体験を優先する。UI側では工程画面・ペギング追跡画面で「受注ごとの状態」を
見せることで、受注単位の見やすさを確保する。

  すでに「発注D+7・必要D+12」という着手日基準のクリティカルパス上にあるため、これを2受注に拡張する形が
  最も自然と判断した
- 具体的な日数表はEXT-1の需要ソート順を踏まえて実装時に`*.test.ts`へ書き起こし、手検証しながら確定する

## §7 実装アーキテクチャ

バックエンドサーバーを持たず、React/TypeScriptのみで完結させる。永続化しない（DBなし）、単一セッション、
シンプルなリクエスト・レスポンスという前提のため、サーバーを置く必然性がない（`mini-simulator`と同じ判断）。

| 層 | 役割 | 実装 |
|---|---|---|
| ドメインロジック | 7ドメインの処理（MRP展開・バックフラッシュ・引当・ペギング・KPI算出など） | 純粋なTypeScript関数群。副作用を持たず、状態を受け取って次の状態を返す |
| 状態管理 | 現在の全ドメイン状態 | ReactのuseReducerで一元管理 |
| 画面 | 状態を表示し、ユーザー操作を受け付ける | Reactコンポーネント |

### action一覧（v5仕様書 §8.2 のユースケースをactionへ対応させたもの）

| action | 対応UC | 役割 |
|---|---|---|
| `SO_CREATE` | UC-04 | 受注登録（`SalesOrder`+`SoLine`を1件ずつ同時生成） |
| `SO_CONFIRM_DELIVERY` | UC-05 | 納期回答確定（EXT-7） |
| `SO_CANCEL` | — | 受注取消（EXT-2・EXT-3のカスケード込み） |
| `MRP_RUN` | UC-06 | `PLANNED_ORDER`全削除→再生成（EXT-1の順序で展開） |
| `PLANNED_ORDERS_FIRM` | UC-07 | 全計画オーダを一括確定（`MFG_ORDER`/`PURCHASE_ORDER`/`WORK_INSTRUCTION`生成） |
| `PO_ACK` | UC-10 | 仕入先納期回答登録 |
| `PO_RECEIVE` | UC-11 | 入荷計上（EXT-4のガード、DEV-3により全量一括のみ） |
| `MFG_RELEASE` | UC-12 | 製造オーダのリリース |
| `WI_START` | UC-13 | 工程着手 |
| `WI_COMPLETE` | UC-14 | 工程完了（良品数・不良数入力、第1工程ならバックフラッシュ） |
| `STOCK_ADJUST` | UC-17 | 棚卸調整 |
| `SHIPMENT_ALLOCATE` | UC-18 | 出荷指示（引当） |
| `SHIPMENT_SHIP` | UC-19 | 出荷実績登録 |
| `ADVANCE_DAY` | UC-22 | `day += 1`のみ |
| `RESET` | UC-23 | 全トランザクション初期化（マスタは保持） |
| `MASTER_ADD_*` / `MASTER_UPDATE_*` / `MASTER_DELETE_*` | UC-01〜03（編集拡張） | 品目・BOM行・工順行・作業区・取引先のCRUD。フィールドごとにactionを増やさず、**エンティティごとに ADD / UPDATE(patch) / DELETE の3本**へ統一する（EXT-20〜EXT-24のガードは`domain/masterData.ts`側で評価する） |
| `MASTER_IMPORT` / `MASTER_RESET_TO_PRESET` | —（EXT-26） | マスタ一式の差し替え。既存トランザクションと整合しないため`RESET`同様に全トランザクションを初期化する |

`checkSchedule()`（UC-08）・`unmetDemand()`（UC-09）・`validateMaster()`（EXT-22）・KPI（UC-20）・
`traceFromOrder()`（UC-21）はいずれも状態から都度計算する導出値であり、専用のactionを持たない。
マスタのJSONエクスポート（`exportMasterSnapshot()`）も状態を変えないためactionを持たない。
