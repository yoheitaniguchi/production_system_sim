## 改善済み下書き

# [要望] テストへの要件ID・工程タグ付与の書式策定（TC-01〜18・TC-E1〜3・TC-M1対象）

## 概要

`src/domain/*.test.ts`のうち、v5-spec.md §9.3のTC-01〜18・§9.5のTC-E1〜3・design.md §6のTC-M1に対応するテストのdescribe/itタイトルへ、要件ID（UC-xx）と工程・テストの種類を示すタグを付与するための書式を策定し、対象ファイル一覧を確定する。実際のタグ付与（リネーム）は別Issueとする。

## 背景・目的

自動テスト管理アプリ（PoC）とこのリポジトリを接続する準備として現状を調査したところ、テストのdescribe/itタイトルにはTC番号（TC-04など）が手動で文字列として埋め込まれている場合があるのみで、v5-spec.md §8.2が定義するUC-01〜23との対応、工程区分（単体/結合/総合）、テストの種類の区分を示す機械可読な印が一切無いことが分かった（`src/domain/mrp.test.ts:11`、`src/domain/schedule.test.ts:10`ほか）。

書式を決めずにいきなりリネームへ進むと、本Issueのレビュー過程で判明したとおり「同じTC番号が複数ファイルにまたがるが検証内容が異なる」「1テストが複数UC/TCの検証を兼ねる」といったケースで判定がぶれ、リネーム後に再修正が発生する。先に書式・判定基準・対象一覧を確定しておくことで、次のリネームIssueを機械的な置換作業として実施でき、UC・工程・テスト種別ごとのテスト網羅状況を外部ツール側で自動集計できるようになる。

## 要件

- 対象は次の13ファイル・該当箇所（TC番号との対応。実ファイルを確認し行番号を検証済み）：
  - `src/domain/exerciseGuide.test.ts:19`（TC-01）
  - `src/domain/salesOrder.test.ts:9`（TC-02〜03）
  - `src/domain/mrp.test.ts:11`（TC-04）, `:68`（TC-05〜06）, `:107`（TC-14）
  - `src/domain/schedule.test.ts:10`（TC-07）, `:21`（TC-E1〜E2）, `:38`（TC-13）
  - `src/domain/procurement.test.ts:18`（TC-07、schedule.test.tsと重複採番）, `:35`（TC-08）, `:57`（TC-10）
  - `src/domain/production.test.ts:27`（TC-09）, `:63`（TC-11〜12）, `:116`（TC-E1〜E3、schedule.test.tsのTC-E1〜E2と一部重複）
  - `src/domain/shipment.test.ts:15`（TC-15〜16）
  - `src/domain/kpi.test.ts:14`（TC-17）
  - `src/domain/pegging.test.ts:9`（TC-18）
  - `src/domain/multiOrderExercise.test.ts:20`（TC-M1）

- 書式案：`[UC-xx][工程][テストの種類] 説明文`。工程は 単体/結合/総合 の3区分、テストの種類は「標準書3章の区分」に合わせるよう依頼されたが、当該文書はリポジトリ内で確認できなかった（`docs/`配下・README.md・CLAUDE.mdを検索したが「標準書」という語が1件もヒットしなかった）ため、本Issueでは区分の呼称を仮に「正常系／異常系」とし、実装時に正式な区分名を別途確認する前提とする

- **工程区分（単体/結合/総合）の判定基準**：1テストにつき区分は必ず1つとし、複数区分の同時付与はしない。基準案：
  - 単体：`domain/*.ts`のエクスポート関数を直接呼び出すだけで、`reducer.ts`（`simulationReducer`/`dispatch`）を経由しない
  - 結合：`reducer.ts`は経由しないが、2つ以上のドメインモジュール（例：`salesOrder.ts`＋`mrp.ts`＋`schedule.ts`）の呼び出し結果を1テストの中でまたいで検証している
  - 総合：`simulationReducer`/`dispatch`を経由し、UI操作と同じaction単位の連鎖として受注〜出荷（またはそれに準ずる範囲）を通す
  - 例：`multiLevelBom.test.ts`は`simulationReducer`経由でマスタ登録〜受注〜MRP〜工程〜出荷〜原価〜ペギングまで通しているため`[総合]`のみとする

- **UCタグの決定基準**：そのit()内で`expect()`により直接検証されている操作を基準に決定する。前提条件を整えるためだけの呼び出し（例：`releaseMfgOrder`を`startStep`の前提として呼ぶだけで結果を検証しない場合）は対象に含めない。1つのit()が複数のTC／UCの検証を1回でまとめている場合は、該当する全UCを`/`区切りで列挙する（例：`[UC-06/UC-07]`）

- UC番号はv5-spec.md §8.2のUC-01〜23に対応させる。対応関係の暫定案（個々のテストの実際の検証内容と異なる場合は次項「重複採番の個別方針」を優先する）：
  - TC-02→UC-04、TC-03→UC-05、TC-04・TC-06・TC-14→UC-06、TC-05→UC-07、TC-08・TC-10→UC-11、TC-09・TC-11・TC-12→UC-13/UC-14、TC-13→UC-09、TC-15→UC-18、TC-16→UC-19、TC-17→UC-20、TC-18→UC-21
  - TC-01（マスタ初期化）・TC-M1（複数受注競合、design.md §6）は特定のUCに対応しないため、工程・テストの種類の印のみとする

- **重複採番（TC-07・TC-E1〜E3）の個別方針**：同じTC番号が複数ファイルに現れても、各テストが実際に`expect()`で検証している内容が異なるため、上記の抽象的なTC→UC対応表をそのまま両方に当てはめず、ファイル・行ごとに個別判定する。
  - `schedule.test.ts:10`（TC-07）：`checkSchedule()`が警告0件であることのみを検証 → `[UC-08]`
  - `procurement.test.ts:18`（TC-07）：`ackPurchaseOrder()`の結果がACKEDになることを検証 → `[UC-10]`
  - `schedule.test.ts:21`（TC-E1〜E2）：`checkSchedule()`の警告1件と、その警告が`affectedSoLine`で受注まで辿れることを検証（TC-E2「警告からペギングを辿る」に相当）→ `[UC-08/UC-21]`
  - `production.test.ts:116`（TC-E1〜E3）：`checkSchedule()`の警告1件に加え、部品未入荷のまま着手→完了を試み`MFG_ORDER`がHOLDになることを検証 → `[UC-08/UC-13/UC-14]`
  - いずれも`ackPurchaseOrder`の呼び出し自体は前提条件としてのみ使われ別途アサーションが無いため、UC-10は`procurement.test.ts:18`にのみ付与する

- 対応するUC番号が明確でないテスト（`masterData.test.ts`・`masterIntegrity.test.ts`・`cost.test.ts`・`lot.test.ts`・`capacity.test.ts`・`dashboard.test.ts`など、v5-spec.mdのUC一覧より後にdesign.mdで追加された機能）については、UC番号を無理に当てはめず、`[工程][テストの種類]`のみの印にとどめる代替書式も許容する

- TC番号はタグ化せず、説明文の中にそのまま残す

- **決定した書式の記録先**：本Issueの本文だけで完結させず、次のリネームIssueが参照できる場所に残す。`design.md`はv5仕様書との業務差分（EXT番号）を記録する場でありテスト命名規約とは性質が異なるため、`docs/issue-workflow.md`と同種の新規ドキュメント（例：`docs/test-tagging.md`）を新設するか、本Issueをリネーム実施Issueから常時参照する運用にするかを、実装着手前に選定する

- 書式の具体例（重複採番の食い違いが分かる例を含む）：
  1. `src/domain/mrp.test.ts:11` の `it("TC-04: 受注 FG-100 x10 / 回答納期 D+15 を展開すると5件の計画オーダが期待どおりの値で生成される", ...)` → `it("[UC-06][単体][正常系] TC-04: 受注 FG-100 x10 / 回答納期 D+15 を展開すると5件の計画オーダが期待どおりの値で生成される", ...)`
  2. `src/domain/schedule.test.ts:21` の `it("TC-E1〜E2: ...", ...)` → `it("[UC-08/UC-21][結合][異常系] TC-E1〜E2: 木板の納期回答が遅れると、親（座面ASSY）の着手日に対する遅延警告が出て受注まで辿れる", ...)`
  3. `src/domain/procurement.test.ts:18` の `it("TC-07: 納期回答を登録するとACKEDになる", ...)` → `it("[UC-10][単体][正常系] TC-07: 納期回答を登録するとACKEDになる", ...)`
  4. `src/domain/schedule.test.ts:10` の `it("TC-07: 希望どおりの納期回答なら警告は出ない", ...)` → `it("[UC-08][単体][正常系] TC-07: 希望どおりの納期回答なら警告は出ない", ...)`（3と同じTC-07でも検証内容が異なるためUCタグが異なる例）
  5. UC番号が明確でない例：`src/domain/multiLevelBom.test.ts` の `describe("4階層BOMをマスタ操作だけで組み立てて通す", ...)` → `describe("[総合] 4階層BOMをマスタ操作だけで組み立てて通す", ...)`

## レビュー時の確認事項

1. **UCタグの決定基準の選択**：本レビューでは「テストが実際に`expect()`で検証している内容を基準にする」案を採用したが、これはv5-spec.md §9.3の「操作」列の文言だけを見ると直感に反する場合がある（例：TC-E1は「納期回答をD+14に変更する」という操作が定義そのものだが、どのテストもその結果自体を直接アサートしていないため、この基準だとUC-10タグがどのテストにも付かない）。この基準でよいか、あるいは「操作」列基準（TC-E1は常にUC-10を含める）を優先するかは、開発チームでの合意が必要。

3. **「テストの種類」区分の正式名称**（"標準書3章"）は本リポジトリ内に存在しないことを確認済み。ユーザー側で当該資料を確認のうえ、正式な区分名（「正常系／異常系」のままでよいか、他の区分も必要か）を教えてほしい。
