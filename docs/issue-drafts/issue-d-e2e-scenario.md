# [要望] 業務シナリオの自動E2Eテストの新設（縮小版スコープ）

## 概要

`docs/v5-spec.md` §9.3の正常系テストケースのうち、受注登録から出荷実績登録までの主要フロー（TC-02・TC-03・TC-04・TC-05・TC-07・TC-08・TC-09・TC-10・TC-11・TC-12・TC-15・TC-16相当）を、Playwrightで自動E2Eテストとして`e2e/scenario.spec.ts`に実装する。既存の`e2e/a11y.spec.ts`（アクセシビリティ検査）とは別ファイル・別npm script・別CIジョブとして独立させる。

## 背景・目的

`e2e/`配下を調査したところ、現状は`e2e/a11y.spec.ts`（axe-coreによるアクセシビリティ検査、ライト/ダーク2テーマ×全タブ）のみが存在し、業務シナリオを実際にブラウザ上で操作して検証するE2Eテストは無い。`src/domain/*.test.ts`はreducerより下のドメインロジック単体テストであり、UIコンポーネント経由の操作導線・画面表示（フォーム入力→ボタン押下→表への反映）は自動検証されていない。

CLAUDE.md「現在の実装状況」には「各画面はPlaywrightで…実際にブラウザで確認済み」という記述が繰り返し登場するが、これらはすべて実装時の**手動確認**（スクリーンショット目視）であり、CIで継続的に自動実行される回帰テストにはなっていない。このため、今後UIリファクタや新機能追加（例：「次にやるべきこと」表の各候補）を行うたびに、受注〜出荷という中核フローが壊れていないかを毎回手動で再確認する必要があり、確認漏れのリスクと確認コストの両方を抱えている。

本Issueを実装すると、受注〜出荷の中核フローについて`npm run test:e2e:scenario`一発でブラウザ操作込みの回帰検知ができるようになり、開発チームメンバーは今後のPRで「手動でブラウザ確認する」記述をCLAUDE.mdに書き足す代わりに、CI結果を根拠にできる（教材としての保守性・レビュー効率の向上）。

なお、自動テスト管理アプリ（PoC）とこのリポジトリを接続する構想が別途あり、それが本Issueの発端ではあるが、**当該PoCとの接続実装自体は本Issueの範囲外**とする（対象範囲外に明記）。

## 要件

1. `e2e/scenario.spec.ts`を、`e2e/a11y.spec.ts`とは別ファイルとして新設する。
2. 以下の縮小版スコープを、1本のPlaywrightテストとして実装する（`docs/v5-spec.md` §9.3の項番に対応。括弧内は画面）。
   - 受注登録 FG-100 x10 希望D+15（TC-02、受注タブ）
   - 納期回答 D+15（TC-03、受注タブ）
   - MRP実行（TC-04、計画タブ）
   - 全計画オーダを確定（TC-05、計画タブ）
   - 仕入先納期回答（希望どおり）（TC-07、発注タブ）
   - D+12まで進め、RM-300を入荷計上（TC-08、発注タブ・時計操作）
   - SA-200 着手→完了（良品10・不良0）（TC-09、工程タブ）
   - D+14まで進め、PT-400・PT-500を入荷計上（TC-10、発注タブ・時計操作）
   - FG-100 着手→工程10 組立完了（良品10・不良0）（TC-11、工程タブ）
   - 工程20 検査完了（良品9・不良1）（TC-12、工程タブ）
   - 出荷指示9個を作成（TC-15、出荷タブ）
   - D+15で出荷実績登録（TC-16、出荷タブ）
   - 各ステップ後、該当画面の表示（在庫タブの現在庫・出荷可能量、SO_LINEのstatus表示等）が期待値どおりであることをアサートする
3. `package.json`に`test:a11y`とは独立したnpm script `test:e2e:scenario`を追加し、`playwright test e2e/scenario.spec.ts --reporter=list,junit`のように**対象ファイルを明示指定**したうえでJUnit形式のレポーターも指定する（出力先は`test-results/e2e-scenario-junit.xml`とし、`docs/issue-drafts/issue-b1-ci-junit-triggers.md`で追加するvitestの`test-results/junit.xml`と衝突しないファイル名にする。Playwrightの`reporter`オプションの`outputFile`設定、または環境変数`PLAYWRIGHT_JUNIT_OUTPUT_NAME`で明示的にパス指定する）。あわせて既存の`test:a11y`スクリプトも`playwright test e2e/a11y.spec.ts`とファイル指定へ変更し、`playwright.config.ts`の`testDir: "./e2e"`により今後`e2e/`配下にファイルが増えても両コマンドが互いを巻き込まないようにする（現状の`playwright test`という無指定呼び出しのままでは、新規specファイル追加時に`a11y`ジョブがシナリオテストも実行してしまうため必須の対応）。
4. `.github/workflows/test.yml`に新規ジョブ`e2e-scenario`を追加し、既存の`test`ジョブ・`a11y`ジョブとは独立させる（`needs`を指定しない並列ジョブとし、それぞれの成否が他方に波及しないようにする）。
5. `a11y`ジョブと同様に`npx playwright install --with-deps chromium`が必要になるが、`actions/cache`で`~/.cache/ms-playwright`をOS・Playwrightバージョン（`package-lock.json`のハッシュ等）をキーにキャッシュし、`a11y`ジョブ・`e2e-scenario`ジョブの両方でキャッシュヒット時はダウンロードをスキップすることで、ブラウザインストールの二重コストを抑える。

## 対象範囲外

- TC-01（マスタ初期化確認）、TC-06・TC-13・TC-14（未充足需要チェック・MRP再実行の山場）、TC-17（KPI確認）、TC-18（ペギング追跡）のE2Eシナリオ化（フルスコープ版として別Issueで検討する）
- TC-E1〜E3（異常系：納期遅延警告・ペギング・HOLD）のE2Eシナリオ化
- TC-M1（複数受注の資源競合演習）のE2Eシナリオ化
- マスタCRUD・原価・ロット追跡・能力計画・演習ガイド・ダッシュボードなど、design.mdで追加された画面（v5-spec.md §9.1のシーケンスに含まれない機能）のE2Eシナリオ化
- 自動テスト管理アプリ（PoC）とこのリポジトリを接続する実装そのもの（CI結果の外部送信、Webhook連携等）。本Issueは同PoCが将来利用しうるE2Eテスト資産をこのリポジトリ内に用意するところまでに限る
